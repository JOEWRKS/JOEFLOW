# U2 계획 초안: 기획툴로서 부족한 부분 (2026-10-31)

상태: 승인 대기. 근거는 오목 실사용 마찰 기록(`_data/joe-tools-friction-log.md` 26건)과 오목 점검 1~9차(`_data/gomoku-audit-log.md`). U1(1.2.0·1.3.0)에서 해결한 항목은 뺐다.

## 1. 진단

JOEFLOW는 **승인한 내용이 바뀌지 않게 지키는 일**은 잘한다. 오목 rev 13~37 동안 승인 digest·재현·대체 연쇄가 모두 맞았다. 부족한 것은 그 앞뒤다.

| 부족한 점 | 증상 (마찰 번호) | 영향 |
|---|---|---|
| A. 작은 일에도 비용이 크다 | 결정 12개 기능에 레코드 37개·바인딩 칸 약 200개, 생성기 200줄 (15·16) | 작은 기능·수정에는 쓰지 않게 된다 |
| B. 질문과 FREEZE 사이 단계가 없다 | 질문을 다 닫으면 상태가 무효 → 가짜 '작성 작업' 질문으로 버팀 (15·26) | 정상 흐름이 우회로가 됨 |
| C. 승인 뒤 바뀌는 상황에 약하다 | 담당자 결정(AGENT)은 대체 불가 (26), DISCOVER 중 요구사항 등록 불가 (7) | 방향 전환 때 기록을 비틀어야 함 |
| D. 근거 모델의 함정 | 추천 근거에 실측을 못 씀 (8), 전달받은 사용자 의도의 근거 종류 없음 (9), 사용자 의도를 질문 근거에 걸면 질문이 사라짐 (8·24) | 맞는 기록이 검증에 막히거나 틀린 기록이 통과 |
| E. 사람이 읽는 결과물을 손으로 쓴다 | 기획서·검토 화면을 rev마다 손으로 갱신 (17, 9차 6), 검토 화면 SVG가 휴대폰에서 6px (17) | rev마다 반복 손작업, 문서와 state 어긋남 |
| F. 시작이 어렵다 | 최소 유효 상태를 만들려고 계약 3개·45KB 스키마·검증기 소스를 읽음 (3), Grill 축 해결 연쇄가 문서에 없음 (14) | 첫 사용 비용이 큼 |
| G. 기존 제품에 기능을 더하는 방식이 없다 | NEW_PRODUCT로 우회 (5) | 실제 불편은 작았음 (아래 3절) |

## 3. U1-8(기능 추가 모드)에 대한 판단

오목은 NEW_PRODUCT로 두고 기존 앱을 근거로만 참조해 37개 revision을 문제없이 진행했다. 우회 비용은 기록 1건이었다. 반면 오목이 실제로 많이 쓴 비용은 A(FREEZE 규모)·B·C였다.

그래서 U1-8을 단독으로 크게 만드는 것보다 **U2-9 경량 FREEZE와 합쳐 설계**하는 것을 추천한다. 기능 추가 모드가 꼭 해야 할 일은 두 가지로 좁힌다.

1. 기존 제품에서 **바꾸면 안 되는 동작**을 근거와 함께 선언(회귀 금지 목록). 구현 인계와 재진입 판정이 이것을 쓴다.
2. 이번에 새로 만들거나 바꾸는 표면만 coverage를 요구.

`EXISTING_PRODUCT_RECONCILIATION`의 intent_classification 요구는 그대로 두고, 새 모드는 표면마다 `change_kind`(NEW·CHANGED·BASELINE)를 가진다. BASELINE 표면은 관찰 근거만 있으면 되고 coverage가 없다. 스키마 버전이 바뀐다(0.3.0 후보).

## 4. 추천 순서

1. U2-1~U2-4 (계약 변경 없음, 바로 효과)
2. U2-5~U2-8을 한 계약 개정으로 (고정 모듈·스키마 해시 갱신 1회)
3. U2-9+U2-10 설계 문서 → 오목 사본 측정 → 에이전트 A/B → 구현 여부 결정
4. U2-11은 보류

각 단계 커밋·푸시·설치·게시는 지금처럼 따로 승인받는다. A/B는 유료 실행이라 횟수를 먼저 묻는다.
