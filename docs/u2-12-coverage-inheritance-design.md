# U2-12 설계 초안: 확정(FREEZE) 칸 수 줄이기 — 측정과 제안 (2026-10-31)

상태: 2026-10-31 사용자 승인, 구현 완료. 구현하며 달라진 점은 6절. 측정 스크립트는 `evals/joeflow-u2-12-coverage-inheritance/`.

처음 안(C')은 "축을 묶어 212칸 → 약 100칸"이었다. 실제 기록 두 개로 재 보니 **축을 묶으면 정보를 잃고, 칸이 많으면 도장 찍듯 채워진다**는 두 사실이 나왔다. 그래서 축은 그대로 두고 칸을 **상속**으로 줄이는 안으로 바꾼다.

## 1. 측정 (오목 rev 38, WebAppDev rev 4 — State 0.2.0을 쓰는 실제 기획 둘)

| | 오목 | WebAppDev |
|---|---:|---:|
| 요구사항 / 화면 / 행동 | 3 / 2 / 5 | 12 / 7 / 44 |
| Core 칸 (20축) | 60 | 240 |
| 화면 상태 칸 (16축) | 32 | 112 |
| 행동 칸 (22축) | 110 (54%) | 968 (73%) |
| 합계(전문 Grill 제외) | 202 | 1,320 |

**축은 중복이 아니다.** 신중하게 쓴 오목은 Core 행마다 20축 중 15~17개가 서로 다른 답이고, 화면 상태 16축 중 14개, 주 행동 22축 중 19개가 다르다. 9묶음짜리 고정 묶음을 대입하면 오목 202칸의 서로 다른 답 157개를 65칸에 넣어야 한다. 묶음 안에서 답이 갈리는 경우가 Core 모든 행·모든 묶음에서 나왔다.

**칸이 많으면 한 레코드로 몰린다.** WebAppDev는 행동 44개 모두 22축 중 14축(64%)이 FLOW 하나에 묶여 있다. 구현하며 다시 보니 각 칸이 그 FLOW의 **다른 단계**(`/paths/9`, `/paths/10`…)를 가리켜 보기보다 의미가 있다. 그래도 한 흐름을 14조각으로 나눠 적는 일이 행동마다 반복된다. 오목은 레코드를 골라 적었고(주 행동 19/22 서로 다름), 둘 다 행동 칸이 전체의 절반 이상이다.

**해당 없음은 행동 모양을 따른다.** 행동별 N/A 축 집합은 두 프로젝트 모두 4가지뿐이다(오목: 고르기 행동 13축, 시작 행동 10축…; WebAppDev: 열기·이동 3축, 조회 4축…). 행동의 종류를 한 번 말하면 N/A 칸은 따라온다.

## 2. 제안: 축은 그대로, 칸은 상속

### A. 행동 모양(shape) 선언
행동마다 `shape`를 둔다(초안: `navigate`·`local_choice`·`submit`·`read_retry`·`destructive`). 모양마다 해당 없는 축 집합이 정해져 있고, 그 축은 적지 않으면 상속 N/A다(U1-7 프로필 상속과 같은 규칙: 적은 칸이 이긴다). 모양 표는 `references/ux-action-shapes-v1.json`에 두고 두 프로젝트의 N/A 패턴에서 만든다. 2026-10-31 안 B(행동 종류 프로필)는 이 안에 포함된다.

### B. 행 기본 근거(default authority)
요구사항·화면·행동 행에 `default_authority`(바인딩 목록)를 한 번 선언한다. 적지 않은 축은 그 바인딩으로 COVERED를 상속한다. 같은 FLOW를 14번 적는 대신 한 번 적고, 다른 답이 있는 축만 쓴다. 펼친 보기에서 상속 칸은 `inherited_from: "row"`로 표시되어 다운스트림과 감사가 손으로 적은 칸과 구분한다. 도장 찍기를 막지는 못하지만, **정직한 기록**으로 바꾼다: "이 행동은 FLOW-003으로 충분하다"고 한 번 말하는 것과, 14칸에 각각 FLOW-003을 적는 것은 다르다.

### 효과 (기존 답을 하나도 바꾸지 않고 펼쳤을 때 같은 칸이 나오는 조건)

## 4. 확인

1. 오목·WebAppDev·Portfolio03: 압축 → 펼침이 원본과 바이트 동일, Manifest·definition digest 동일, closure 결과 동일.
2. 상속이 근거 없이 일어나지 않음: 모양 없는 행동·기본 근거 없는 행에서 생략 칸은 누락 오류.
3. 모양 표가 두 프로젝트의 N/A 패턴을 전부 설명하는지(설명 못 하는 행동은 개별 N/A로 남김).
4. 에이전트 A/B: 같은 기능을 0.2.0 방식과 0.3.0 방식으로 FREEZE해 칸 수·도장 비율(한 레코드가 차지하는 비율)·누락 비교. 유료 실행이라 횟수는 따로 묻는다.
5. 전체 회귀.

## 5. 순서와 규모

1. 모양 표 + `expand_coverage` + 검증 변경 + 스키마·dispatch 0.3.0 + 고정 해시 (가장 큰 묶음)

## 6. 구현 결과 (2026-10-31)

- **State 0.3.0을 만들지 않았다.** `definition_digest`가 `schema_version`을 포함해, 버전을 올리면 기존 승인이 모두 낡은 것이 된다. 또 다운스트림 2.1 계약이 `state_schema_version = 0.2.0`을 확인한다. 그래서 `shape`·`default_authority`는 **0.2.0 안의 작성 형식**이다. 정식 형식은 펼친 상태이며, 검증·digest·다운스트림은 모두 펼친 보기(`expand_coverage`)를 읽는다. 고정 스키마 파일은 펼친 형식을 그대로 기술하므로 바꾸지 않았다. 설명은 `references/coverage-inheritance.md`.
- 고정 모듈 변경: `authority_binding_v2.py`(펼친 보기 검증, 행 선언 허용, 상속 칸 규칙, `unknown_action_shape`), `approval_v2.py`(digest 투영을 펼친 보기로). `grill_v2.py`·`binding_diagnostics.py`·downstream_v2 seeds·reentry는 고정이 아니다.
- **손실 없는 압축 결과**(`compact_coverage.py`, 펼침 바이트 동일·두 digest 동일·검증 동일 확인):

  | | 오목 rev 38 | WebAppDev | Portfolio03 |
  |---|---:|---:|---:|
  | 빠진 칸 | 38 / 202 (19%) | 209 / 1,320 (16%) | 0 (coverage가 OPEN) |

  2절의 추정(28·589)과 다른 이유: 추정은 **레코드**가 같은 칸을 셌지만, 상속은 **바인딩**(레코드+위치+해시)이 같아야 손실이 없다. WebAppDev는 같은 FLOW라도 축마다 다른 위치(`/entry`·`/paths`…)를 가리켜 기본 근거 하나로 묶이지 않는다. 손으로 쓴 N/A는 근거·사유가 있어 모양 상속으로 바꾸면 기록이 달라지므로 압축하지 않는다. 그래서 **A(모양)는 새 행에서 효과가 나고, 기존 승인본은 B만** 적용된다.
- 모양 표 5개는 두 프로젝트의 N/A 패턴 8가지를 모두 포함한다(패턴은 모양 집합의 부분집합).
- 확인 1·2·3·5 완료. 4(에이전트 A/B)는 유료라 실행하지 않았다.
