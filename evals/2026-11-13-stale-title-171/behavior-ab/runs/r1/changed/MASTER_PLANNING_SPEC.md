## 1. 제품, 사용자, 목표, 범위

- 목표 `GOAL-001`: 요청자가 유효한 요청을 끝까지 제출한다.
- 사용자 `USR-001`: 로그인한 요청자(REQUESTER).
- 요구사항 `REQ-001`: 요청자는 유효한 요청을 제출할 수 있다. 범위는 기본 요청 작업 흐름이며 화면이 필요하다(`ui_required: true`).
- 범위 표면 `SURF-001` "Request submission": IN_SCOPE, 근거 `REQ-001`.
- 범위 밖(사용자 확인 `EVD-900`에 따른 N/A): 결제(MONEY), 파일 업로드, 비동기 처리, 권한(PERMISSION) 구분, 파괴적 작업.
  인증(AUTH) 검토 묶음은 활성이지만 로그인·로그아웃·세션 만료·비밀번호 재설정 등 세부 축은 `EVD-900` 근거로 N/A이고, 등록(registration) 축만 `RULE-001`로 다룹니다.
- 외부 연동 `INT-001` "Request API": 받아들인 요청을 저장한다.

## 2. IA, 이동, 돌아가기

- 화면은 하나입니다: `SCR-001` 요청 폼.
- 진입: 요청 폼을 연다(`FLOW-001` entry). 전제: 요청자가 로그인되어 있다(`FLOW-001` preconditions).
- 나가기·돌아가기: 제출 후 이동할 화면이나 돌아가기 동작은 정의되어 있지 않습니다(정의된 결과는 "요청이 받아들여진다"까지).

## 3. 공통 규칙, 데이터, 상태

- `RULE-001`: 유효한 요청만 제출할 수 있다(`DEC-001`, 사용자 결정 `UNK-001` → 선택지 "검증 후 제출"; 그 결과 유효하지 않은 요청은 거부된다).
- `RULE-002` (rev 2 추가): 요청 내용 칸 아래 오른쪽에 '현재 글자 수 / 200'을 보이고, 글자를 넣거나 지울 때마다 바로 바꾼다(`DEC-002`).
- 데이터 `DATA-001` "Request": 요청 입력을 담는다. 소유: 요청자.
- 상태 `STATE-001` `REQUEST_READY` (`SCR-001`): 필수 입력이 유효하다.
- "유효함"의 구체 항목(필수 칸 목록, 형식 규칙)은 `state.json`에 따로 정의되어 있지 않습니다. 이 문서는 그 내용을 지어내지 않습니다.

## 4. 화면 명세 — `SCR-001` 요청 폼

- 목적: 요청을 제출한다. 상호작용 화면(INTERACTIVE). 주요 동작: 제출(submit). 관련 요구사항 `REQ-001`.
- 입력: 요청 내용 칸은 textarea 하나이고 최대 200자다(`EVD-902`, 2026-11-12 구현 관찰. 200자 한도는 관찰된 사실이며 이 revision에서 새로 정한 정책이 아닙니다).
- 글자 수 표시 (rev 2, `RULE-002` / `DEC-002`): 요청 내용 칸 아래 오른쪽, 형식 '현재 글자 수 / 200', 글자를 넣거나 지울 때마다 즉시 갱신, 입력 중 항상 보임. 빈 칸은 '0 / 200'(`AC-002`).
  - 검토한 다른 안 `NEAR_LIMIT`(180자부터만 표시)은 선택되지 않았습니다(`UNK-002`).
  - 대가: 칸 아래에 한 줄이 늘어난다.
- 상태: 기본, 로딩, 빈 입력, 부분 입력, 제출 중, 성공·완료, 오류, 비활성 등 UX 상태 칸은 `ux_coverage`에서 모두 COVERED이며 근거는 `SCR-001`, `FLOW-001`, `RULE-001`, `STATE-001`, `AC-001`, `DEC-001`에 묶여 있습니다. 유효하지 않으면 제출이 거부되고(`RULE-001`), 필수 입력이 유효하면 `REQUEST_READY`입니다(`STATE-001`).
- 쓰기: 받아들인 요청은 `INT-001`을 통해 저장된다(`AC-001`).

## 5. 사용자 흐름 — `FLOW-001`

요청자 입장에서: 로그인한 상태로 요청 폼을 열고, 요청 내용을 적는 동안 칸 아래 오른쪽 '현재 / 200'을 보며 길이를 맞춘 뒤 제출합니다.

| 단계 | 내용 | 근거 |
|---|---|---|
| 진입 | 요청 폼을 연다 | `FLOW-001` entry |
| 전제 | 요청자가 로그인되어 있다 | `FLOW-001` preconditions |
| 입력 중 | 글자 수 표시가 즉시 바뀐다 | `RULE-002`, `AC-002` |
| 시스템 판단 | 요청을 검증한다 | `FLOW-001` paths, `RULE-001` |
| 성공 | 요청이 받아들여지고 저장된다 | `FLOW-001` outcomes, `AC-001`, `INT-001` |
| 실패 | 유효하지 않은 요청은 제출되지 않는다(거부) | `RULE-001`, `DEC-001` |

복구 방법(오류 문구, 입력 유지 여부)과 제출 후 다음 화면은 정의되어 있지 않습니다.

## 6. 동작 계약 — 제출(submit)

- 행위자: `USR-001` 로그인한 요청자. 대상: `DATA-001` Request.
- 전제: 로그인 상태(`FLOW-001`), 필수 입력이 유효함(`STATE-001`).
- 실행: 요청을 검증한 뒤 제출한다(`DEC-001`).
- 성공(유효할 때만): 요청이 받아들여지고 `INT-001`로 저장된다(`AC-001`).
- 거부(유효하지 않을 때만): 제출되지 않는다(`RULE-001`). 이 거부는 유효하지 않은 경우에만 해당하며 일반 결과가 아닙니다.
- 글자 수 표시는 입력 중 동작이며 제출 결과를 바꾸지 않습니다(`RULE-002`).

### 투영 충실도 원칙

- 승인 대상의 조건과 분기를 그대로 둔다.
- 예외 경로를 모든 성공·실패의 결과로 바꾸지 않는다.
- 근거가 없는 분기는 쓰지 않는다. 필요하면 Product Definition으로 돌아간다.

## 7. 완료 기준

- `AC-001` (`REQ-001`, 작업 `TASK-001`): 유효한 요청은 받아들여지고 저장된다.
- `AC-002` (`REQ-001`, 작업 `TASK-002`, rev 2 추가): 요청 내용에 글자를 넣거나 지우면 칸 아래 오른쪽 표시가 즉시 '현재 글자 수 / 200'으로 바뀐다. 빈 칸은 '0 / 200'.

## 8. 반응형, 접근성, 이후 선택 경계

- 승인 대상 제품 요구: 위치(칸 아래 오른쪽), 형식('현재 / 200'), 즉시 갱신, 항상 보임.
- 이후 시각·기술 선택(글자 크기, 색, 화면 읽기 프로그램 안내 방식 등)은 정의되어 있지 않으며 이 문서가 정하지 않습니다.

## 9. 남은 것, 외부 확인, 승인 상태

- 열린 제품 질문: 없음(`UNK-001`, `UNK-002` 모두 RESOLVED; Manifest의 semantic-closure 차단 항목 0).
- 승인: revision 2는 아직 승인되지 않았습니다. 사용자가 위 Approval Manifest digest를 승인해야 합니다.
- 확인 권장: `DEC-002`는 다른 세션이 전달한 사용자 원문 "요청 내용 칸에 글자 수 보여줘"(`EVD-901`)를 추천안 `BELOW` 수락으로 기록했습니다. 원문은 위치를 고르지 않았으므로, 승인 때 위치·표시 방식(항상 보임)을 사용자가 직접 확인하는 것이 좋습니다.
- 구현 관찰(`EVD-902`)과 렌더 확인은 제품 질문이 아니라 검증 항목입니다.
