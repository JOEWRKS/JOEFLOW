작성일: 2026-10-23. 적용 절차: `planning-skill/SKILL.md` → `references/workflow-v0.2.0.md`, `discovery-contract-v0.2.0.md`, `grill-contract-v0.2.0.md`, `interrogation-engine.md`, `unknown-taxonomy.md`, `ux-state-taxonomy.md`, `product-coverage-matrix.md`, `grill-packs/core.json`, `grill-packs/async.json`.

## 1. 근거

### 1.1 사용자 요청 (원문)

> "지금 오목 게임을 AI 보조 도우미가 실제로 작동하는 AI 대국 오목 게임으로 만들어봐. 서로 대화를 주고받는게 아니라 추천 수와 경우의 수, 상대의 예상 수와 각 위치 별 승률을 가시적으로 알려주는 제한적 알고리즘을 쓰는 거임. 상호작용하는 LLM이 아니라."

요청에서 확정적으로 읽히는 의도:

- R1. LLM이나 대화형 도우미가 아니라 **결정적이고 제한된 로컬 알고리즘**이어야 합니다. 현재 구현 방식(외부 AI API 없음, 로컬 Worker)과 맞습니다.
- R2. 사람과 AI가 실제로 **대국**해야 합니다.
- R3. 다음 네 가지를 **시각적으로** 보여 줘야 합니다. (a) 추천 수, (b) 경우의 수, (c) 상대의 예상 수, (d) **각 위치별 승률**.
- R4. 대화형 문장보다 시각화가 중심입니다("서로 대화를 주고받는게 아니라").

요청에서 모호하거나 빠진 부분은 2장의 미결 결정으로 등록했습니다.

### 1.3 발견한 모순과 간극 (DISCOVER 결과)

- **C1. 승률 표시와 BRIEF의 충돌(가장 중요).** 새 요청은 "각 위치별 승률"을 요구합니다. BRIEF, DESIGN, 현재 UI는 근거 없는 퍼센트 승률을 명시적으로 금지합니다. BRIEF의 조건은 "근거가 없다면"입니다. 따라서 (가) 근거를 갖춘 산출 방법을 새로 정의하거나, (나) 사용자가 BRIEF 제약을 바꾸거나, (다) 퍼센트가 아닌 표현으로 대체하는 것 중 하나를 사용자가 **명시적으로** 선택해야 합니다. 이 충돌은 알아차린 것만으로는 해결되지 않습니다.
- **C2. "AI 보조 도우미가 실제로 작동하는"의 의미.** 현재 앱은 검사상 추천·해설·응수가 작동합니다. 요청은 (가) 체감상 작동하지 않는다고 느낀 것(버튼을 눌러야 AI가 두는 것, 텍스트 위주), (나) AI가 자동으로 두는 진짜 대국을 원함, (다) 분석이 너무 빈약함(추천 1곳뿐) 중 하나로 읽힙니다. 증거만으로는 확정할 수 없습니다.
- **C3. 정체성 변화.** 현재 제품은 "함께 배우는" 학습형(한 문장 해설, 수동 진행)입니다. 요청은 "대국 + 시각적 분석" 중심입니다. 기존 학습 문장과 학습 흐름(review 단계)을 유지·축소·제거할지가 열려 있습니다.
- **C4. 현재 엔진의 출력 부족.** "경우의 수"와 "위치별 값"을 보여 주려면 후보별 점수, 예상 수순, 판 전체 값 맵을 엔진이 내보내야 합니다. 이는 분석 계약(`Analysis`, `ENGINE_VERSION`)의 변경입니다. 이 자체는 구현 사항이지만, 무엇을 노출할지는 제품 결정입니다.
- **C5. 계산 비용(비동기 팩 활성화).** 위치별 값을 225칸 전체 또는 시뮬레이션으로 계산하면 현재의 2초 watchdog과 모바일 성능에 부딪힙니다. 대기, 부분 결과, 시간 초과, 취소 후 늦은 결과가 실질적인 제품 동작이 됩니다. `GRILL-ASYNC-1`이 활성화되며, partial_completion과 duplicate_execution 축은 MATERIAL 하한입니다.

### 1.5 활성 Grill 팩

- `GRILL-CORE-1`: 항상 활성입니다.
- `GRILL-ASYNC-1`: 활성 판단입니다(Worker 분석은 ASYNC_PROCESS, 계산량 증가). pending, timeout, retry, cancel, late_completion, partial_completion(MATERIAL), duplicate_execution(MATERIAL), idempotency(MATERIAL), reconciliation(MATERIAL)이 해당합니다. 이 가운데 idempotency, duplicate_execution, reconciliation은 기존 검증된 계약(요청 식별 일치, 늦은 결과 거절, AI 돌 중복 방지)을 그대로 유지하는 것으로 증거상 해결할 수 있다고 봅니다. partial_completion만 사용자 결정으로 남깁니다(UNK-008).
- auth, money, permission, file-upload, destructive-action: 비활성입니다. 계정·결제·업로드가 없습니다. 새 게임 확인은 기존 동작입니다.

## 2. 사용자에게 물을 미결 결정 (우선순위순)

순위 기준: 파급 범위 → 기존 권위 원본(BRIEF)과의 충돌 → 핵심 흐름 → 상태/복구 → 부가 선호. 실제 진행에서는 **한 번에 한 질문**만 묻고, 답을 기록한 뒤 영향을 받는 항목을 재평가합니다.

### UNK-001 [최우선 · USER_DECISION_REQUIRED] "각 위치별 승률"을 무엇으로, 어떤 근거로 표시할까요?

- 중요한 이유: BRIEF는 근거 없는 퍼센트 승률을 금지합니다. 이 결정은 엔진, 표시 형태, 도움말 문구, 계산 비용(UNK-007·008), 검증 방식 전체를 좌우합니다.
- 선택지:
  - **A. 로컬 시뮬레이션 승률(측정 근거가 있는 퍼센트).** 각 후보 위치에 두었다고 가정하고, 이 앱의 AI끼리(약간의 무작위성 포함) N판을 끝까지 둡니다. 흑이 이긴 비율을 "시뮬레이션 승률 62% (40판 기준)"처럼 표시합니다. 장점: 사용자가 원하는 "승률" 숫자를 제공하고, 산출 근거(판 수·방법)를 밝힐 수 있어 BRIEF 조건을 충족합니다. 단점: 계산이 무겁고(모바일에서 수 초), "이 AI끼리의 승률"이지 사람 대 사람의 승률은 아니라는 한계 문구가 필요합니다. 판 수가 적으면 오차가 큽니다.
  - **B. 퍼센트 없는 유불리 단계 히트맵.** 각 빈칸을 "매우 유리 / 유리 / 비슷 / 불리 / 즉시 패배 위험" 5단계 색과 기호로 표시합니다. 기존 2 ply 평가에 근거합니다. 장점: 빠르고 BRIEF와 충돌하지 않습니다. 단점: 사용자가 말한 "승률" 숫자가 없습니다.
  - **C. 평가 점수를 퍼센트로 변환(BRIEF 제약 변경).** 휴리스틱 점수를 로지스틱 함수로 0–100%에 매핑합니다. 장점: 빠르고 숫자가 보입니다. 단점: 실제 확률 근거가 없어 BRIEF를 변경해야 하고, 사용자를 오도할 위험이 있습니다.
- **권장: A + B 혼합.** 상위 후보 몇 곳(UNK-004)에는 시뮬레이션 승률 숫자와 표본 수를 함께 보여 주고, 나머지 주변 칸은 B의 단계 히트맵으로 보여 줍니다. 퍼센트는 근거가 있는 곳에만 붙이고, "이 앱의 AI끼리 둔 결과이며 실제 승패 예측이 아님"이라는 한계를 함께 적습니다. C는 권하지 않습니다.

### UNK-002 [2순위 · USER_CONFIRMATION] AI는 사람이 착수한 뒤 자동으로 둘까요?

- 중요한 이유: "실제로 작동하는 AI 대국"의 핵심 흐름입니다. 지금은 `AI 응수 보기` 버튼을 눌러야 AI가 둡니다. 상태 기계, 되돌리기, 예상 수 표시 시점이 함께 바뀝니다.
- 선택지:
  - **A. 자동 응수.** 흑 확정 → 분석 → 백이 자동 착수(짧은 지연, 예: 0.5초) → 다음 흑 분석. 예상 백 수는 착수 전 잠깐 표시하거나 직전 분석 기록에 남깁니다.
  - **B. 현재처럼 수동 진행.** review 단계에서 버튼을 눌러야 백이 둡니다.
  - **C. 설정으로 선택(기본 자동).** "AI 응수 전 멈춤" 토글을 둡니다.
- **권장: A.** 진짜 대국 느낌을 우선하고, 예상 수는 분석 패널에 기록으로 남깁니다. C는 화면 요소를 늘리므로 사용자가 학습용 멈춤도 원할 때만 고릅니다.

### UNK-003 [3순위 · USER_DECISION_REQUIRED] "경우의 수"는 무엇을 보여 줘야 하나요?

- 선택지:
  - **A. 후보별 예상 수순.** 각 추천 후보마다 "내 수 → 상대 최선 응수 → 내 다음 수…"를 판 위에 번호 고리(①②③)로 미리 보여 줍니다(2–4수).
  - **B. 탐색 규모 통계.** "후보 12곳, 검토한 경우 144가지" 같은 숫자를 표시합니다.
  - **C. 후보 목록 표.** 후보 좌표, 평가, 승률, 상대 최선 응수를 표로 나열합니다.
- **권장: A + C.** 판에서는 선택한 후보의 수순을 번호 고리로 보여 주고, 패널에는 후보 목록 표를 둡니다. B는 보조 한 줄로 충분합니다.

### UNK-004 [4순위 · USER_CONFIRMATION] 추천 수와 위치별 값은 몇 곳에 보여 줄까요?

- 선택지: **A.** 상위 3곳만 표시. **B.** 상위 5곳은 숫자, 그 밖의 주변 후보는 색 단계로 표시. **C.** 225칸 전체 히트맵.
- **권장: B.** 390px 화면에서 숫자가 겹치지 않고, 계산 비용도 감당할 수 있습니다. C는 의미 없는 먼 칸까지 칠해 판이 시끄러워지고 계산 비용이 큽니다.

### UNK-005 [5순위 · USER_CONFIRMATION] "상대의 예상 수"는 언제, 몇 곳을 보여 줄까요?

- 선택지:
  - **A.** 내 착수 직후 상대(AI)의 유력 응수 상위 3곳(1순위 강조).
  - **B.** 착수 전, 내가 선택하거나 마우스를 올린 후보 칸에 대해 "여기 두면 상대는 X에 둘 것" 1–2곳.
  - **C.** A와 B 모두.
- **권장: C.** 착수 전에는 선택 후보의 상대 응수를 보여 줘 수순 미리보기(UNK-003 A)와 통합하고, 착수 후에는 상위 3곳을 보여 줍니다. 모든 표시에는 "가능한 대응이며 확정된 미래가 아님"을 유지합니다(BRIEF).

### UNK-006 [6순위 · USER_CONFIRMATION] 분석 표시는 항상 켜져 있어야 하나요?

- 선택지: **A.** 항상 표시. **B.** 켜기/끄기 토글(기본 켬). **C.** 요청 시에만 표시(분석 보기 버튼).
- **권장: B.** 분석 없이 실력으로 두고 싶은 대국도 가능하게 합니다. 끄면 계산을 생략해 저사양 기기 부담을 줄일 수 있습니다.

### UNK-007 [7순위 · USER_CONFIRMATION] AI의 실력과 탐색 깊이를 높일까요?

- 중요한 이유: 지금은 2 ply입니다. 자동 대국과 "승률"이 의미를 가지려면 AI가 너무 약하면 안 됩니다. 반면 BRIEF는 프로 수준 엔진이 불필요하다고 하고, 강도를 검증하지 않은 주장을 금지합니다.
- 선택지: **A.** 2 ply 유지. **B.** 위협 탐색(연속 4·3 강제수 확인)과 깊이 4 내외로 강화하되, 시간 예산 안에서 단일 난이도로 운영. **C.** 난이도 선택(쉬움/보통/어려움) 추가.
- **권장: B.** 강도 수치는 주장하지 않습니다. C는 범위 확장이므로 별도 요청 시에만 진행합니다.

### UNK-008 [8순위 · USER_DECISION_REQUIRED · async partial_completion] 계산이 길어질 때 부분 결과를 보여 줄까요?

- 중요한 이유: 시뮬레이션 승률은 시간이 걸립니다. 현재 계약은 "완료된 결과만 표시하고, 2초 초과 시 간이 분석"입니다.
- 선택지:
  - **A. 점진 표시.** 추천과 상대 수는 먼저 보여 주고, 승률은 "계산 중 18/40판"처럼 갱신합니다. 시간 예산이 끝나면 그때까지의 표본 수로 확정 표시합니다.
  - **B. 완료 후 일괄 표시.** 시간 예산을 넘기면 승률 칸을 "계산 못 함"으로 표시합니다.
  - **C.** 사용자가 착수하면 진행 중 계산은 취소하고, 부분 결과는 버립니다(A·B 공통 부가 규칙).
- **권장: A + C.** 표본 수를 항상 함께 표시해 부분 결과가 확정 값처럼 보이지 않게 합니다. 판이 바뀌면 진행 중 계산과 늦은 결과는 기존 계약대로 폐기합니다.

### UNK-009 [9순위 · USER_CONFIRMATION] 기존 한 문장 해설과 학습 화면은 어떻게 할까요?

- 선택지: **A.** 유지하고 시각 분석 패널을 추가. **B.** 짧은 라벨 한 줄(예: "방어: 백 5목 위협 차단")로 축소하고 시각 분석 중심으로 재구성. **C.** 제거.
- **권장: B.** "대화가 아니라 가시적으로"라는 요청에 맞춥니다. 즉시 승리·방어 같은 사실 라벨은 시각 표식만으로는 이유가 드러나지 않으므로 남깁니다. 제품명("함께 배우는")과 안내 문구 변경 여부도 함께 확인합니다.

### UNK-010 [10순위 · USER_CONFIRMATION] 종료 후 복기에 당시 분석(추천·승률·예상 수)도 보여 줄까요?

- 선택지: **A.** 각 수의 당시 분석 스냅샷을 저장해 복기에 표시(재계산 없음). **B.** 복기는 현재처럼 돌과 해설만 표시.
- **권장: A.** 메모리 사용이 늘지만 수순 학습 가치가 큽니다. 저장 범위는 상위 후보 요약으로 제한합니다.

### UNK-011 [11순위 · USER_CONFIRMATION · 범위] 사람이 백(후공)도 선택할 수 있어야 하나요?

- 선택지: **A.** 흑 고정 유지(BRIEF). **B.** 시작 시 색 선택.
- **권장: A.** 이번 범위에서는 유지하고, 필요하면 후속 요청으로 다룹니다.

> 미결이지만 질문하지 않는 사실 항목: 현재 엔진이 실제로 작동하는지는 검사 증거(단위 62·E2E 18 통과, `checks.txt`)로 해결됩니다. 따라서 "현재 AI가 정말 작동하나요?"는 묻지 않습니다. C2의 해석만 UNK-002로 묻습니다.

## 3. 담당자가 정할 비중요 결정 (AGENT_AUTONOMOUS 후보)

모두 국소적이고 되돌릴 수 있으며, 위 사용자 결정의 의미를 바꾸지 않는 범위입니다.

- 히트맵 색 팔레트, 단계 경계값, 범례 위치. 색만으로 구별하지 않도록 기호나 숫자를 병행합니다(기존 DESIGN 원칙).
- 퍼센트 표기 형식(정수 %, 표본 수 괄호 표기), 숫자 글자 크기, 판 위 라벨 충돌 처리(겹치면 패널로 이동).
- 수순 미리보기 번호 고리 모양, 상대 수와 내 수의 고리 스타일 구분(실선/점선/색).
- 자동 응수 지연 시간(0.3–0.8초 범위)과 동작 감소 설정 시 애니메이션 제거.
- 시뮬레이션 판 수(N), 롤아웃 무작위성, 시간 예산, Worker 분할 방식 등 내부 파라미터. 사용자에게는 표본 수만 노출합니다.
- 엔진 데이터 계약 확장(`Analysis`에 후보 목록·수순·값 맵 추가), `ENGINE_VERSION` 갱신, 요청 식별 계약 유지.
- 분석 패널의 탭이나 섹션 구성, 데스크톱과 모바일 배치 세부(데스크톱 오른쪽 패널, 모바일 판 아래).
- 접근성: 각 교차점의 aria 이름에 단계·승률 포함("H8, 빈칸, 유리, 시뮬레이션 62%"), live 알림 빈도 제한.
- 토글 상태를 세션 메모리에만 두는 방식(영구 저장 없음, 기존 원칙).
- 검사 설계: 결정성 시드 고정 단위 검사, 값 맵과 판의 일치 검사, 자동 응수 중복 방지 E2E, 두 지정 화면 렌더 확인.
- 간이 분석(fallback) 시 승률과 수순 칸을 숨기고 "간이 분석: 승률 계산 안 함"을 표시하는 문구.
- 도움말에 새 표식 설명과 한계 문구 추가.

### 4.2 주요 사용자 흐름

**FLOW-001 대국 한 차례 (자동 응수, 권장안)**

1. 새 게임 → 빈 판 → 흑 분석 요청(thinking).
2. 분석 완료(human): 히트맵, 추천 상위 5, 1순위 수순 미리보기가 표시되고, 승률은 점진적으로 채워집니다.
3. 사용자가 칸을 선택합니다. 그 칸이 후보면 해당 수순과 상대 예상 응수를 표시합니다. 후보 밖이면 "이 칸 분석"을 요청하거나(구현 결정) 단계 색만 표시합니다.
4. `H8에 두기`로 확정합니다. 진행 중 계산은 취소되고 늦은 결과는 버립니다.
5. 흑 착수가 반영됩니다. 승리하면 종료(FLOW-003)로 갑니다.
6. 백 분석(thinking, "AI가 생각 중"): 상대 예상 상위 3곳을 점선으로 표시하고, 직전 수 요약 라벨을 표시합니다.
7. 짧은 지연 후 백이 자동 착수합니다(한 번만, 중복 방지). 승리 또는 무승부이면 종료합니다.
8. 1단계(다음 흑 분석)로 돌아갑니다.

**FLOW-002 분석 실패와 복구**: 분석 오류 또는 시간 초과 → 판을 보존 → 간이 분석으로 진행(승률·수순 숨김, 한계 표시) → [다시 분석]으로 Worker를 재생성합니다. 백 자동 응수는 간이 분석 결과로 계속 진행합니다(기존 계약). 성공한 것처럼 꾸민 값은 만들지 않습니다.

**FLOW-003 종료와 복기**: 종료 → 결과와 승리선 → [대국 복기] → 0수부터 이전/다음 수 → 각 수의 당시 분석 스냅샷 → [종료 판으로] / [새 게임].

**FLOW-004 되돌리기**: 내 차례 또는 AI 생각 중에 [↶ 되돌리기]를 누르면 직전 흑 수와 그 뒤 백 수를 일괄 취소합니다. 진행 중 계산을 취소하고, 복원된 판에서 분석을 다시 계산합니다(기존 계약 유지). 자동 응수 지연 중에 되돌리면 예약된 백 착수를 취소합니다.

**FLOW-005 분석 켜기/끄기**: 토글을 끄면 판 표식과 패널을 숨기고 이후 분석 계산을 생략합니다(AI 착수용 최소 탐색만 수행). 다시 켜면 현재 판을 즉시 분석합니다.

**FLOW-006 새 게임**: 대국 중이면 확인 후 초기화합니다. 모든 진행 중 계산, 예약된 자동 응수, 이력이 취소되고 늦은 결과는 거절됩니다.

### 4.3 수용 기준 초안 (관찰 가능)

- AC-a: 흑이 확정하면 사용자 추가 조작 없이 백이 정확히 한 번 착수합니다(UNK-002 A 채택 시).
- AC-b: 표시된 모든 퍼센트 옆이나 패널에 산출 방법과 표본 수가 있습니다. 표본 없이 퍼센트만 단독으로 표시되는 곳이 없습니다(UNK-001).
- AC-c: 추천, 수순, 히트맵, 상대 예상 수는 모두 현재 판(gameId·revision·key)과 일치합니다. 판이 바뀐 뒤 도착한 결과는 표시되지 않습니다.
- AC-d: 간이 분석 시 승률과 수순이 표시되지 않고 한계 문구가 보입니다.
- AC-e: 1440×900과 390×844에서 판 표식이 겹쳐 읽을 수 없게 되지 않고 가로 넘침이 없습니다.
- AC-f: 외부 네트워크 요청이 0이고 LLM이나 외부 API를 쓰지 않습니다.
- AC-g: 되돌리기, 새 게임, 복기의 기존 회귀 검사가 통과합니다.

### 4.4 다음 단계 (이 문서 이후)

1. UNK-001부터 한 번에 하나씩 사용자에게 묻습니다(선택지와 권장 포함).
2. 답을 받을 때마다 결정을 기록하고, 영향받는 UNK(특히 001 → 004·007·008, 002 → 005·FLOW-004)를 재평가합니다.
3. 모든 MATERIAL 미결 결정이 닫히면 FREEZE, APPROVE, HANDOFF로 넘어갑니다. 이 단계들은 이번 작업 범위 밖입니다.
