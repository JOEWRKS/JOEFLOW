`DEC-001`에 따라 제품은 한 도매·납품업체가 사용하는 단일 조직용이다. 조직 선택기, 복수 사업부 데이터 분리, 다중 고객 테넌트, 플랫폼 운영자 콘솔과 요금제는 만들지 않는다.

`DEC-002`에 따라 케이스 오너가 접수부터 완료까지 전체 책임을 유지한다. `DEC-028`에 따라 권한 있는 RMA Agent는 조직 전체 케이스·감사 이력을 조회하되 현재 케이스 오너만 결정·배정·면제·완료하며, `DEC-034`~`DEC-037`의 `final resolution` 최초 확정 뒤 적격 미커밋 결과 배분·부분 수량 범위 재개와 범위별 원자적 정리 게이트도 현재 케이스 오너만 시작한다. `DEC-038`에 따라 실행 커밋 뒤 오류·분쟁 범위의 별도 연결 정정 케이스에서 현재 케이스 오너가 정정·보상 유형과 사유·증빙을 결정하고, carrier·warehouse·settlement simulation이 보상 사건을 실행·기록하며 다른 범위와 원 케이스 완료는 계속한다. `DEC-077`에 따라 보상 사건 실행 직전에는 원 참조·결정·증빙·simulation별 불가역 효과·현재 정정 케이스 버전을 상세 표시해 현재 오너가 명시 확인하고, 취소하면 저장 입력·체크포인트를 유지한다. 실행 커밋된 결정·보상 사건은 불변이며 추가 오류·분쟁은 같은 연결 정정 케이스에 원 사건을 불변 참조하는 후속 사건으로 표시한다. `DEC-031`에 따라 공급사 지정 택배 inbound 회수의 운송사·운송장 번호와 추적 상태는 현재 케이스 오너가 등록·갱신하고, 거래처 부담 발송은 거래처 사용자가 자기 조직 포털에서 등록·갱신한다. 현재 오너는 두 방식의 누락·오류·예외를 검토하고 감사 이력을 남겨 정정한다. 창고 담당자는 배정된 입고·검수 작업, `DEC-074`의 배정된 `REPLACEMENT` 출고 작업, `DEC-051`의 배정된 `NO_CREDIT` 물리 작업 및 필요한 문맥만 조회하고 해당 전문 필드만 변경한다. `REPLACEMENT` 출고에서는 범위 상세 확인 뒤 로컬 재고 차감과 carrier simulation 인계를 같은 유일 실행 참조로 수행·기록하되 final resolution이나 예외를 결정하지 않는다. 회수 운송장 기준 필드는 읽기 전용이다. `DEC-030`에 따라 현재 케이스 오너가 별도 outbound `RETURN_TO_CUSTOMER` 반환 운송장 생성·발송 인계·직접 인수 증거·추적 갱신을 모두 직접 수행·기록하며 별도 실행 역할을 두지 않는다. 정산 담당자는 배정된 `REFUND` 작업과 필요한 문맥만 조회·변경하지만 `final resolution`을 다시 열거나 연결 정정 케이스의 정정·보상 결정을 할 수 없다. 거래처 사용자는 자기 거래처 조직의 외부 공개 정보만 보고 허용된 요청·보완·이의를 제출하며 결과 재개·정리와 연결 정정 상태는 읽기 전용으로만 확인한다. 창고 작업공간과 거래처 포털에도 재개·정정 결정 행동을 만들지 않는다. 오너 인계는 권한 있는 RMA Agent 사이에서 사유와 감사 이력을 남긴다. `DEC-029`, `DEC-032`에 따라 `NO_CREDIT` 금전 처리는 settlement simulation이 자동 실행·기록하고 현재 케이스 오너가 정산 예외·요율 보완·재계산 통제·이의 검토·사유 있는 면제·연결 작업 완료와 자동 처리 실패 작업을 소유한다. `NO_CREDIT` 재고 차단·격리·폐기 실행은 `DEC-051`의 현재 오너 통제·배정 창고 담당자 실행·필수 증거 경계를 따르고 `DEC-059`·`RULE-059`에 따라 내부 사용자는 조직 SSO와 MFA를 `SIMULATION`으로 사용하고 거래처 사용자는 비밀번호와 `SIMULATION` 이메일 OTP를 사용한다. 두 경로 모두 30분 미사용 또는 8시간 절대 경과 시 세션을 만료하고 연속 행동, 이메일 성공 기산, 재시도 횟수·간격, 새 역할·새 화면은 만들지 않는다. `DEC-070`은 기존 `SCR-001`의 운영·SLA 지표·필터, 같은 필터 제한 CSV, 제외 필드와 실행 감사만 투영한다. `DEC-071`은 불가역 실행 직전 범위별 상세 명시 확인·취소 시 비커밋 체크포인트 유지·감사를, `DEC-072`는 연결 단절 때 서버 체크포인트와 현재 탭 임시 보존·같은 멱등 키 재시도·자동 병합 금지를, `DEC-073`은 저장분·미저장분을 구분한 draft 삭제 명시 확인·즉시 삭제·복구 없음·감사를 투영한다. `DEC-074`는 현재 오너의 `SCR-002` 확정·배정 뒤 배정 창고 담당자가 `SCR-003` 별도 `REPLACEMENT` 출고 단계에서 대상 범위·추적값·재고 전후·불가역 효과·범위 버전을 확인하고 로컬 재고 차감과 carrier simulation 인계를 같은 유일 실행 참조로 수행한 뒤 공통 케이스로 복귀하는 흐름을 투영한다. `DEC-075`는 `SCR-004` 연결 사건의 성공 서버 체크포인트·현재 탭 임시 보존·시간 초과 결과 우선 조회와 조건부 재시도·충돌 시 최신 상태 우선·`IN_TRANSIT` 직접 제출 차단·재인증 뒤 체크포인트 재개를 투영하되 기기 영구 저장·오프라인 편집/제출/동기화와 자동 병합을 만들지 않는다. `DEC-076`은 `SCR-002` 케이스 완료 직전 상세 확인, 취소 시 기존 `ACTIVE` 유지·완료 사건 없음, 완료 뒤 undo·원 케이스 재개 없음과 이후 `DEC-038` 연결 정정을 투영한다. `DEC-077`은 연결 정정 보상 사건 직전 원 참조·결정·증빙·불가역 효과·현재 정정 케이스 버전의 상세 확인, 취소 시 저장 입력·체크포인트 유지, 실행 커밋된 결정·사건 불변과 같은 연결 정정 케이스의 후속 사건을 투영한다.

`DEC-058`·`RULE-058`은 기존 `SCR-001` 업무 목록, `SCR-002` 케이스 작업공간, `SCR-003` 검수·물리 전문 작업공간과 `SCR-004` 거래처 포털 사이의 진입·복귀 관계를 고정한다. 공통 케이스 요약·타임라인과 감사 계보를 유지하고 역할별 작업함에서 배정 전문 작업으로 직접 진입한 뒤 완료 시 공통 케이스로 복귀한다. 새 화면 구성, 반응형 동작, 데스크톱·태블릿·모바일 우선순위는 이 결정에서 추정하거나 추가하지 않는다.

`DEC-032`와 `RULE-041`은 모든 시각 구조에 적용할 dogfood 데이터 경계다. 주문·납품과 상품·정책은 실행 중 불변인 결정적 로컬 fixture, 케이스·품목별 요청·결정·결과·작업·감사 이력은 RMA 앱, 입고·검수·`REPLACEMENT` 예약·출고 재고·로컬 출고 차감·`NO_CREDIT` 재고 차단·격리·처분은 `INT-005` 결정적 로컬 창고 상태 저장소, 회수·`REPLACEMENT` 교환 출고·`RETURN_TO_CUSTOMER` 운송 이벤트는 `INT-004` carrier simulation, `REFUND`와 `NO_CREDIT` 금전 단계는 `INT-006` settlement simulation을 원천으로 사용한다. 실제 API·웹훅·배치·외부 운영 원장 파일 가져오기·내보내기와 실제 주문·재고·운송·금전·이메일 부수효과는 만들거나 암시하지 않는다. `DEC-046`의 역할 제한 로컬 RMA 케이스 패키지와 `DEC-070`의 허용 분석 행 제한 CSV는 외부 운영 원장 파일 연동이 아니다. 모든 fixture·로컬 상태·simulation 기반 데이터·행동·상태·결과·감사 기록에는 `DOGFOOD FIXTURE`, `DOGFOOD LOCAL`, `CARRIER SIMULATION`, `SETTLEMENT SIMULATION` 또는 `SIMULATION` 원천을 명시한다.

`DEC-003`에 따라 한 케이스는 정확히 한 주문의 여러 품목을 담고 품목별 부분 승인·입고·검수·결과 배분을 허용한다. 서로 다른 주문의 품목을 한 케이스에 섞지 않는다.

`DEC-004`에 따라 혼합 일반 도매 상품을 다루며 각 품목은 추적 없음·시리얼·로트 중 하나를 적용한다. 시리얼은 개별 단위, 로트는 로트별 수량으로 기록한다.

`DEC-005`에 따라 시리얼·로트 품목은 접수 추적값이 필수이고, 입고 검수에서 요청값과 대조하며, 교환 출고품의 별도 추적값이 필수다.

`DEC-006`, `DEC-032`에 따라 품목 추적 방식은 `INT-001`의 불변 `DOGFOOD PRODUCT FIXTURE`에서 고정하고 케이스와 검수 화면에서는 읽기 전용 원천 표식과 함께 표시한다. 사용자가 이를 바꾸는 선택기나 수정 행동을 만들지 않는다.

`DEC-007`에 따라 케이스 생성 당시 추적 방식을 스냅샷으로 고정한다. 이후 로컬 fixture 변경은 기존 케이스에 반영하지 않고 새로 생성하는 케이스에만 적용한다.

`DEC-008`, `DEC-032`에 따라 상품 fixture 추적 방식이 없거나 지원되지 않으면 새 케이스 생성을 차단하고 해당 SKU의 로컬 fixture 정정 필요성을 안내한다. 실행 중 케이스를 수정하거나 실제 상품 마스터 정정 요청을 보내는 행동, `NONE` 기본값과 케이스 예외 수정은 만들지 않는다.

`DEC-009`에 따라 시리얼 신원은 조직 전체에서 유일하며 같은 값의 별도 신원 생성은 차단한다. 요청·입고 관찰은 같은 신원을 참조하고, 정정은 기존 값과 전후·사유·수행자·시각을 보존하는 교체로 처리한다.

`DEC-010`에 따라 시리얼은 앞뒤 공백만 제거하고 나머지 문자·구분자·대소문자를 보존한 값으로 조직 전체 중복과 단계 일치를 정확 비교한다.

`DEC-011`에 따라 로트 행은 번호·수량이 필수이고 제조일·유통기한·공급 로트는 선택이다. 같은 케이스 품목·단계에서 여러 로트 분할과 동일 로트 행 병합을 허용하고 합계는 단계 품목 수량과 맞아야 한다.

`DEC-012`에 따라 로트 번호는 앞뒤 공백만 제거하고 나머지 문자·구분자·대소문자를 보존한 값으로 동일 행 병합과 단계 일치를 정확 비교한다.

`DEC-013`에 따라 거래처가 요청 등록·증빙 보완·결과 확인까지 하는 전체 포털을 포함한다. 거래처 사용자는 자기 조직 범위만 보고 내부 메모·전문 작업과 다른 거래처 데이터는 볼 수 없다.

`DEC-014`에 따라 포털을 기본 접수 채널로 하고 전화·이메일 요청은 내부 케이스 오너가 원 요청자와 채널을 남겨 대리 등록한다. 자동 API·ERP·이메일 유입은 만들지 않는다.

`DEC-015`에 따라 요청 품목의 거래처 계약·상품별 반품 가능 기간과 허용 사유를 자동 판정하고 적용 정책·버전·입력·결과를 저장한다. 기준 밖 요청은 자동 거절하지 않고 예외 승인 대기로 전환한다.

`DEC-016`에 따라 거래처 계약 정책을 우선 적용하고 계약 정책이 없으면 상품 정책을 적용한다. 두 정책이 모두 없으면 자동 거절하지 않고 예외 승인 대기로 전환한다.

`DEC-017`에 따라 각 요청 품목의 반품 가능 기간은 거래처가 해당 품목을 실제로 수령한 납품 완료일부터 계산한다.

`DEC-018`에 따라 현재 승인 권한이 있는 RMA Agent인 케이스 오너가 정상·예외 모두 품목별 승인·거절·추가정보요청을 결정한다. 별도 금액 한도는 없으며 승인 수량은 주문라인 납품수량에서 이미 확정된 이전 반품수량을 뺀 값을 넘을 수 없다. 별도 승인 관리자나 상위 금액 승인 흐름을 만들지 않는다.

`DEC-019`에 따라 승인 품목이 불량·오배송이면 공급사 지정 택배와 공급사 부담으로 회수하고, 단순 반품이면 거래처 부담으로 발송한다. 모든 회수 배송은 발송 확정 전 운송사·운송장 번호를 필수 기록해 추적한다. `DEC-031`에 따라 공급사 지정 택배는 현재 케이스 오너가 운송사·운송장 번호와 추적 상태를 등록·갱신하고, 거래처 부담 발송은 거래처 사용자가 자기 조직 포털에서 등록·갱신한다. 현재 오너는 두 방식의 누락·오류·예외를 감사형 정정하고 창고는 읽기 전용 운송장 문맥을 실제 입고에 연결한다. 따라서 `SCR-004`는 `REQ-003`을 포함해 자기 조직 거래처 부담 발송 등록·갱신 행동과 공급사 지정 택배 읽기 전용 상태를 표현해야 한다. `DEC-032`에 따라 진행 이벤트는 `INT-004` carrier simulation이 결정적으로 실행·기록하고 모든 운송 상태에 `CARRIER SIMULATION`을 표시하며 실제 배송은 일어나지 않는다. `DEC-040`에 따라 `DATA-011` inbound 대상 품목·부분 수량 범위가 실제로 `IN_TRANSIT`로 전이된 사건·시각부터 그 범위의 거래처 직접 변경·취소 접수만 닫는다. 운송장 등록만으로는 닫지 않고 거래처 부담 회수 운송장 등록·추적 갱신, 다른 범위와 `DATA-012` outbound `RETURN_TO_CUSTOMER` 배송은 계속 구분한다. 중복 갱신·재시도 복구는 `DEC-044`, 알림은 `DEC-045`·`RULE-045`에서 확정한다.

`DEC-020`·`DEC-065`에 따라 입고 검수에서 SKU·수량·추적값을 공통 대조하고 품목·부분 수량별 포장 상태 `INTACT`/`DAMAGED_OR_OPENED`, 제품 상태 `NORMAL`/`DEFECT_CONFIRMED`, 재판매 가능성 `YES`/`NO`를 독립 항목으로 기록한다. 단순 반품은 포장·외관·구성품, 불량은 신고 증상·기능 재현·외관·구성품, 오배송은 요청·승인 대비 실제 SKU·수량·추적값과 상품 라벨, 추적 불일치는 요청·승인 추적값과 실제 입고 추적값을 체크한다. 손상·불량·오배송·추적 불일치는 증빙이 필수다. `DEC-046`에 따라 접수·보완·검수·이의·처분을 포함해 v1 dogfood가 지원하는 모든 증빙 업로드 형식은 JPG·PNG·PDF만 허용하고 영상 파일 선택·업로드 기능은 만들지 않는다. `DEC-057`에 따라 파일당 최대 20 MB로 제한하고 별도 파일 개수·제출 단위 총량 상한은 두지 않으며, 확장자·MIME·파일 시그니처 일치와 결정적 로컬 악성 파일 검사를 모두 통과한 파일만 첨부로 확정한다. 형식·용량·검사 실패·시간 초과·검사기 오류 파일은 확정하지 않고 사유를 표시해 안전한 파일을 다시 선택하게 하며, 다른 유효한 Draft 입력과 이미 확정된 안전한 첨부를 보존하고 실패·재업로드를 같은 업무 참조에 연결한다. 재판매 등급·검수 대기 값·추가 사유 분류는 만들지 않는다.

`DEC-021`에 따라 승인 내용과 실제 입고 SKU·수량·추적값이 다르면 불일치한 품목·수량만 보류하고 일치한 부분과 다른 품목은 병렬로 계속 처리한다. 검수 화면은 현재 오너가 배정한 창고 담당자에게만 열리고 불일치 상세·조건부 증빙·보류 수량 등 검수 전문 필드만 변경하게 한다. 케이스 작업공간은 현재 오너의 실제 입고 인정·거절에 따른 보류 해제와 추가정보요청 중 보류 유지를 표현해야 한다. 인정하려는 총수량이 원 승인 수량보다 많으면 먼저 승인 가능 수량 범위의 재승인을 요구한다. 케이스 완료는 모든 품목·수량이 종결되고 각 결과에 적용할 완료 기준을 충족할 때만 허용하며, `DEC-048`에 따라 모든 `NO_CREDIT` 수량의 폐기 증거가 기록되거나 물리적 예외가 해결된 상태를 필수로 한다.

`DEC-022`에 따라 검수·재결정이 끝난 품목별 수량에는 고정 매트릭스를 적용한다. 단순 반품·재판매 가능은 `REFUND`, 확인된 불량·오배송은 `REFUND` 또는 `REPLACEMENT`, 단순 반품·재판매 조건 미충족 또는 불량·오배송 미확인은 `RETURN_TO_CUSTOMER` 또는 `NO_CREDIT`만 허용하고 RMA Agent가 사유를 기록한다. 일반 `REJECT`를 최종 처리 코드로 만들지 않는다. 케이스 작업공간에는 허용 코드·부분 수량·사유, 검수 화면에는 판정 입력과 결과 조회, 포털에는 외부 공개 코드·수량·사유가 필요하다.

`UNK-062`~`UNK-069`은 `ANSWERED`이며 `DEC-034`~`DEC-044`에 따라 현재 케이스 오너만 결과 배분·부분 수량 범위별 `final resolution`을 최초 확정·재개하고, 커밋된 범위만 잠그며 미커밋 형제 범위와 다른 품목은 계속 처리한다. `DEC-037`의 원자적 정리 게이트와 실패 범위 `REOPEN_CLEANUP_HOLD`, `DEC-038`의 커밋 뒤 범위별 연결 정정과 불변 원 참조를 표시한다. `REFUND`는 `DEC-067`의 `TRANSFER_ACCEPTED` 전, `REPLACEMENT`는 `DEC-066`의 같은 유일 실행 참조에 로컬 재고 출고 차감과 carrier simulation 운송 접수 성공이 모두 기록되기 전, `RETURN_TO_CUSTOMER`는 실물 인계 또는 직접 인수 서명 전, `NO_CREDIT`는 폐기 실행 시작 전까지 적격 범위만 재개한다. `REFUND` 이체 요청·`TRANSFER_ACCEPTED` 전 실패와 `REPLACEMENT`의 전량 예약·확정·출고 준비·새 추적값 기록은 커밋이 아니다. `REFUND` 지급 커밋·완료 사건과 증거는 `DEC-067`, `REPLACEMENT` 역할·예약·출고·커밋 증거는 `DEC-066`으로 확정됐다. 제출 뒤 변경·취소는 `DEC-040`~`DEC-043`의 `IN_TRANSIT` 마감·최소 되돌림·고정 분기·필드별 증거 매핑을 따른다.

`DEC-023`에 따라 `RETURN_TO_CUSTOMER`는 공급사가 추적 가능한 반환 배송을 주선하고 거래처가 운송비를 부담한다. 운송사 배송 완료 또는 거래처 직접 인수의 서명·수령 확인 전에는 완료할 수 없고 분실·파손·배송 실패·미인수는 예외로 유지한다. `DEC-035`에 따라 라벨 생성·결과 통지는 비커밋 준비 상태이고 운송사 실물 인계 또는 거래처 직접 인수 서명부터 실행 커밋이다. 케이스 작업공간에는 주선·비용·운송 또는 직접 인수 참조·상태·완료 증거·예외를, 포털에는 주선자·비용 부담·참조·상태·각 시각을 표시한다. `DEC-030`에 따라 현재 케이스 오너가 이 outbound 반환 운송장 생성·발송 인계·직접 인수 증거·추적 갱신을 모두 직접 수행·기록하고 별도 실행 역할을 두지 않는다. `DEC-062`에 따라 운송사 배송은 거래처 수취 착불이고, 현재 오너의 실물 인계 뒤 carrier simulation 운송 접수 성공과 함께 결과 배분·부분 수량 범위별 `KRW` 운임을 확정해 포털에 금액·착불 상태를 공개한다. 라벨 값은 미확정으로 표시하고 착불 회수 성공과 배송 완료를 하나의 성공 사건으로 표시한다. 회수 실패는 배송 완료로 표시하지 않고 `DEC-050` 배송 실패·미인수 연결 정정 상태로 보낸다. 승인 뒤 공급사로 회수하는 inbound 운송장의 `DEC-031` 회수 방식별 등록·갱신 책임과 혼합하지 않으며, `DEC-028`이 창고 담당자를 배정된 입고·검수 작업으로 제한하므로 검수 화면에 `RETURN_TO_CUSTOMER` 후속 실행 쓰기 행동을 만들지 않는다. `DEC-050`에 따라 운송사 실물 인계 뒤 carrier 배송 예외는 현재 오너가 범위별 연결 정정 케이스에서 건별 해결·기록하고 carrier simulation 실행·필수 증거 확인 뒤 종결한다. `DEC-063`에 따라 결정적 로컬 주문 fixture의 원 납품처 주소·수령 연락처를 자기 조직 포털 기본값으로 제시하고 거래처의 확인 또는 대체 값 요청 뒤 현재 오너가 운송사 인계 전에 목적지·연락처 스냅샷을 확정하며 원 fixture와 감사 계보를 보존한다. 실제 외부 결제·청구 동작이나 직접 인수 비용 필드는 만들지 않는다.

`DEC-024`·`DEC-047`·`DEC-049`에 따라 `NO_CREDIT` 수량은 통지 성립 시각부터 판매 가능 재고에서 제외해 연속 336시간 동안 주말·공휴일 포함·연장 없이 무상 격리하고 이후 공급사가 폐기하며 거래처가 폐기 비용을 부담한다. `DEC-035`에 따라 통지·격리·금액 계산은 비커밋이고 폐기 실행 시작부터 커밋이다. `DEC-047`에 따라 필수 통지 내용과 단일 참조, 포털 원자 게시·거래처 조회 가능 시각, 같은 참조의 보조 이메일 복구를 표시한다. `DEC-048`에 따라 모든 대상 수량의 폐기 증거 또는 물리적 예외 해결을 케이스 완료 게이트로 표시하고 폐기비 정산 예외는 독립 추적한다. 요율 미확정이면 확정 금액 대신 정산 예외와 근거를 표시하며 이메일 실패는 물리 상태를 되돌리지 않는다. 기간 계산은 `DEC-049`를 따르고 정상 재고 차단·격리·폐기 실행·증거는 DEC-051을 따르고 제한 품목은 DEC-052, 보관 사고는 DEC-053에서 확정했고 폐기 실패·부분 성공은 DEC-054로 확정됐다.

`DEC-025`에 따라 `NO_CREDIT` 폐기비는 거래처 계약 고정 요율을 우선하고 없으면 품목 고정 요율을 적용한다. `INT-006` settlement simulation의 처리 상태·실패·정산 예외를 물리 처리와 구분한다. `DEC-047` 통지에는 확정 폐기비와 산정 근거를 포함하고 요율이 없으면 `DEC-025`·`DEC-026` 정산 예외와 근거를 대신 식별한다. 자기 조직 포털 원장 게시가 거래처에 조회 가능해진 시각에 연속 336시간을 시작하고, 보조 이메일 실패는 같은 참조 재전송·현재 오너 에스컬레이션으로만 표현하며 금전·물리 상태를 되돌리지 않는다. 실제 금전·이메일 부수효과는 없다.

`DEC-026`에 따라 `NO_CREDIT` 폐기비 요율 없음·차감 실패 예외는 현재 케이스 오너 RMA Agent가 소유한다. 현재 오너는 요율 보완·재계산을 통제하고 사유 있는 면제와 연결 작업 완료를 결정한다. `DEC-029`, `DEC-032`에 따라 settlement simulation은 보완된 요율로 재계산하고 차감 실패 시 다음 두 모의 정산에서 자동 재차감하며, 계속 실패하면 모의 미수금으로 전환·기록한다. 자동 처리 실패는 같은 현재 오너 소유 작업으로 전환한다. 로컬 격리·폐기는 계속하고 케이스는 선택된 물리 완료 기준으로 닫되 연결 정산 작업은 회수 또는 현재 오너의 사유 있는 면제까지 유지한다. 내부 업무 목록과 케이스 작업공간에는 `SETTLEMENT SIMULATION` 표식과 함께 예외 소유자, 자동 실패 작업, 재계산 전후, 재차감 회차·결과, 모의 미수금·회수, 면제 사유와 완료된 케이스의 연결 작업을 보여야 한다.

`DEC-027`에 따라 거래처는 `DEC-047` 통지 성립 시각부터 336시간이 지나기 전까지 자기 조직 포털로 폐기비 이의를 접수한다. 현재 케이스 오너 RMA Agent가 검토하며 `DEC-029`, `DEC-032`에 따라 settlement simulation이 검토 결과에 맞춰 모의 차감 전에는 이의 금액만 보류하고 차감 후에는 해당 금액만 사후 조정해 `SETTLEMENT SIMULATION` 감사 이력에 기록한다. 자동 처리 실패는 같은 현재 오너 소유 작업으로 전환하고, 이의는 로컬 물리 처리와 케이스 완료를 막지 않는다. 포털에는 통지 성립 참조·성립 시각부터 336시간 뒤 이의 기한·이의 금액·검토 상태·결과를, 내부 업무 목록과 케이스 작업공간에는 현재 오너 검토·simulation 자동 보류 또는 사후 조정 상태·실패 작업과 감사 이력을 표시한다. 이의 증빙의 형식·파일당 용량·검사·실패 복구는 `DEC-057`을 적용하고 별도 폐기비 이의 검토 완료 기한은 `DEC-068`에서 정하지 않는다.

`DEC-028`은 시각 구조의 권한 경계다. RMA Agent 전체 조회와 현재 오너의 실행 가능 상태, 감사형 오너 인계, 배정된 입고·검수 창고 작업, 배정된 `REFUND` 정산 작업, 자기 거래처 조직 외부 포털을 명확히 구분해야 한다. `DEC-034`~`DEC-037` 재개와 범위별 정리는 현재 오너가 같은 Return Line의 적격 미커밋 결과 배분·부분 수량 범위에 사유를 필수로 남겨 시작하는 행동으로만 표현한다. 정리 중인 범위의 새 실행은 차단하고, 성공 전 새 resolution 버전을 활성화하지 않으며, 실패한 범위만 `REOPEN_CLEANUP_HOLD`로 표시한다. 커밋된 범위만 잠그고 미커밋 형제 범위는 다시 열거나 재개 없이 기존 확정 결과대로 계속 처리할 수 있으며 케이스와 Return Line의 커밋·미커밋 혼재를 유효한 상태로 표시한다. `DEC-038`의 커밋 뒤 연결 정정은 오류·분쟁 범위마다 별도 케이스로 표현하고 원 케이스·범위·resolution 버전·커밋 증거 불변 참조, 현재 오너의 정정·보상 유형·사유·증빙 결정, carrier·warehouse·settlement simulation 보상 사건, 다른 범위와 원 케이스의 계속 처리를 함께 표시한다. `DEC-050`의 `RETURN_TO_CUSTOMER` carrier 배송 예외는 이 연결 정정 구조 안에서 현재 오너의 건별 경로·추가 비용 처리 결정·기록, carrier simulation 실행·필수 증거 확인과 종결로 표현하고 원 resolution 재개나 고정 해결 순서를 만들지 않는다. 창고 담당자에게는 새 결정·실행 행동 없이 필요한 배정 문맥만, 거래처 포털에는 기존 외부 공개 분류의 상태·결과만 읽기 전용으로 표시하고 구체 공개 필드를 추가하지 않는다. 정산 담당자에게도 재개나 연결 정정 결정 행동을 주지 않는다. `DEC-031`의 inbound 회수 운송장은 현재 오너의 공급사 지정 택배 등록·갱신·두 방식 감사형 정정, 거래처 사용자의 자기 조직 거래처 부담 발송 등록·갱신, 창고의 읽기 전용 문맥·실제 입고 연결로만 표현한다. `DEC-040`의 직접 변경·취소 접수 마감은 이 inbound 대상 범위가 `IN_TRANSIT`가 된 사건으로만 표현하고 운송장 등록, 다른 범위, outbound `RETURN_TO_CUSTOMER` 상태에는 적용하지 않는다. `DEC-029`, `DEC-032`에 따라 `NO_CREDIT` 금전 단계는 `SETTLEMENT SIMULATION` 자동 처리 상태와 현재 오너의 예외·요율 보완·재계산 통제·이의 검토·면제·완료·자동 실패 작업으로 표현하며, 수동 금전 실행 버튼이나 별도 담당자 큐를 만들지 않는다. `DEC-030`의 outbound `RETURN_TO_CUSTOMER` 실행은 현재 케이스 오너의 직접 행동으로만 표현하고 별도 담당자 큐나 창고 쓰기 행동을 만들지 않는다. DEC-051에 따라 SCR-002의 현재 오너 범위별 배정·예외·완료 검토와 SCR-003의 배정 창고 담당자 물리 실행·필수 증거 기록만 제공하고 다른 화면·역할에 물리 실행 버튼이나 담당자 큐를 만들지 않는다. 화면 어디에서도 실제 외부 시스템의 연결·처리 완료를 암시하지 않는다. `DEC-042`의 여섯 분기는 범위별 권한과 함께 적용해 포털의 허용 보완·폐기비 이의, 현재 오너의 조건부 미커밋 재개·커밋 뒤 정정, 일반 변경·취소 차단과 혼합 쟁점 분리를 같은 동작으로 합치지 않는다. `DEC-046`에 따라 현재 케이스 오너만 해당 케이스의 전체 내부 패키지를 다운로드하고, 거래처 사용자는 자기 거래처 조직의 외부 공개 패키지만 다운로드한다. 창고·정산 담당자에게 전체 내부 패키지 다운로드나 배정 문맥 밖 일괄 다운로드를 제공하지 않으며, 어떤 역할에도 자동 삭제 설정·실행 또는 수동 hard-delete UI를 제공하지 않는다.

## 화면별 dogfood 데이터 경계

`DEC-044` 표현 경계: 각 쓰기 동작은 멱등 키와 대상 범위 예상 버전을 전달하되 비밀 원문 대신 표시 가능한 요약만 보여 준다. 같은 키·같은 입력은 기존 진행·결과로, 같은 키·다른 입력과 버전 불일치는 충돌·최신 상태 재조회로 표현한다. simulation 실행 카드는 결과 배분 범위·resolution 버전·동작별 유일 실행 참조와 진행·성공·실패 결과를 표시하고, 감사 패널은 멱등 키·입력 요약·예상 및 실제 버전·효과 참조·반환 결과를 노출한다. 새 버튼·역할·화면 목적지는 만들지 않는다.

`DEC-045` 표현 경계: 포털 원장·작업함·이메일은 모두 RMA 앱 안의 기록과 상태로만 표현하고 실제 이메일 전송 또는 외부 전달 성공을 암시하지 않는다. 일반 지정 사건의 이메일 성공·실패를 업무 상태 전이로 만들지 않는다. `DEC-047`의 `NO_CREDIT` 예외는 자기 조직 포털 원장의 원자 게시가 거래처에 조회 가능해진 시각을 통지 성립·연속 336시간 기산으로 표시하고, 보조 이메일 성공·실패는 그 성립과 물리 상태를 바꾸지 않게 한다.

- `SCR-001`: RMA 케이스·작업·감사 이력은 RMA 앱, 주문·상품·정책은 불변 로컬 fixture, 운송은 carrier simulation, 재고·창고는 로컬 상태 저장소, 금전 처리는 settlement simulation에서 읽고 모든 모의 상태를 명시한다. 실제 외부 연동·부수효과는 없다. 조직 전체 조회 권한 RMA Agent에게 `DEC-070`의 운영·SLA 대시보드와 같은 필터의 집계 및 케이스·품목·결과 배분 범위 분석 행 제한 CSV만 제공한다. CSV에서 증빙 파일·원문 감사 이벤트·연락처·정산 계좌를 제외하고 실행 감사를 표시한다. 이벤트 원장 대량 반출·JSON·추가 개인정보 필드는 제공하지 않으며, 해당 케이스의 현재 오너에게만 전체 내부 패키지 다운로드를 제공한다.
- `SCR-002`: 불변 fixture 주문·Order Line·상품·정책·상업 스냅샷과 carrier·settlement simulation 및 로컬 창고 상태를 출처별로 표시하고, 실제 API·웹훅·배치·외부 운영 원장 파일 연동과 실제 외부 부수효과를 제공하지 않는다. 해당 케이스의 현재 오너에게만 전체 내부 패키지 다운로드를 제공하며 이 로컬 산출물을 외부 운영 원장 파일 내보내기로 표현하지 않는다.
- `SCR-003`: 입고·검수 관찰, `REPLACEMENT` 로컬 재고 출고 차감, `NO_CREDIT` 재고 차단·격리·처분은 결정적 로컬 창고 상태 저장소에 기록한다. carrier simulation의 inbound 회수 상태와 `REPLACEMENT` outbound 인계·운송 접수 결과를 해당 결과 배분·부분 수량·resolution 버전·유일 실행 참조에 연결하고 실제 창고·재고·운송 시스템에는 쓰지 않는다. 모든 로컬·모의 상태를 명시한다. 창고 담당자에게 전체 내부 패키지 다운로드나 배정 문맥 밖 일괄 다운로드를 제공하지 않는다.

## 실행 가능한 다운스트림 계약

제품정의는 `CLOSED`지만 이번 승인 기록 범위에는 `joewrks.action-conformance/1.0` 계약, 라이프사이클 계약, SHA-256, 어댑터, 고정 소스 커밋과 시퀀스 러너 생성이 포함되지 않았다. 이 부재는 downstream 미착수 경계이며 회귀 슬라이스나 임의 테스트로 대체할 수 없다.
