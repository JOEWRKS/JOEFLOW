## DEC-065 엄격한 2값 검수 계약

## DEC-066·RULE-066 REPLACEMENT 전량 예약·교환 출고 커밋 계약

- 현재 케이스 오너가 `REPLACEMENT` 결과 배분·부분 수량을 최초 확정하기 직전에 결정적 로컬 재고를 범위 전량으로 원자 예약한다. 성공한 범위만 확정·출고 준비하고 SERIAL 또는 LOT 품목의 새 출고 추적값을 기록한 뒤 창고 담당자에게 출고 작업을 배정한다.
- 배정된 창고 담당자가 결정적 로컬 창고 상태에서 출고 수량을 차감해 carrier simulation에 인계한다. 로컬 재고 출고 차감과 carrier simulation 운송 접수 성공이 같은 범위·resolution 버전·동작의 유일 실행 참조로 모두 기록된 때만 해당 범위를 교환 출고 커밋으로 잠근다.

- 품목·부분 수량별 승인 또는 추가정보요청 결정, 실제 입고 연결 뒤 검수 완료, 검수·재결정 완료 뒤 final resolution 확정, 확정 뒤 배정 전문 작업 시작에 각각 8업무시간 목표를 적용한다.

- `SCR-002` 내부 대리 등록과 `SCR-004` 거래처 포털의 draft 작성·증빙 업로드·제출은 성공한 서버 저장만 권위 체크포인트로 사용한다. 연결 단절·불안정 중에는 새 저장·제출을 차단하고 미전송 입력은 현재 열린 탭 메모리에만 유지해 저장분·미저장분을 구분한다.
- 재연결하면 `DEC-044`의 같은 멱등 키·예상 범위 버전으로 다시 저장한다. 충돌하면 최신 서버 상태를 먼저 읽고 자동 병합하지 않는다.
- 탭 종료·새로고침·`DEC-059` 세션 만료 뒤에는 마지막 서버 체크포인트에서 재개한다. 기기 영구 저장·오프라인 편집·오프라인 제출·동기화는 만들지 않는다. `DEC-056`의 전면 장애 수기 대기열과 `DEC-069`의 `SCR-003` 전용 계약은 그대로 유지한다.

## DEC-073·RULE-073 draft 삭제 확인·복구 없음 계약

- 수행자·시각·draft 참조·확인 또는 취소 결과를 감사한다. 제출 뒤 불변 요청 스냅샷·연결 사건은 삭제하지 않는다.

## DEC-074·RULE-074 REPLACEMENT 전문 출고 계약

## DEC-075·RULE-075 연결 변경·취소·정정 사건 복구 계약

- `UNK-074`는 사용자 답변 A에 따라 `ANSWERED` 처리되어 `DEC-075`로 닫혔다.
- 성공한 서버 저장만 연결 사건의 권위 체크포인트로 사용하고 연결 단절·불안정 중 새 저장·제출을 차단하며 미전송 입력·첨부 대기는 현재 열린 탭 메모리에만 유지한다.
- 시간 초과에는 같은 멱등 키의 저장된 진행·결과를 먼저 조회하고 결과가 없을 때만 같은 키·예상 범위 버전으로 재시도한다. 충돌하면 최신 서버 상태를 먼저 읽고 자동 병합하지 않는다.
- 최신 상태가 `IN_TRANSIT`이면 직접 제출을 차단하고 `DEC-042` 경로만 표시한다. 탭 종료·새로고침·세션 만료 뒤에는 재인증 후 마지막 성공 서버 체크포인트에서 재개하며 기기 영구 저장·오프라인 편집·제출·동기화는 만들지 않는다.

## DEC-076·RULE-076 케이스 완료 확인·완료 후 비재개 계약

- `UNK-075`는 사용자 답변 A에 따라 `ANSWERED` 처리되어 `DEC-076`과 `RULE-076`으로 닫혔다.
- 케이스 완료 직전에 현재 오너에게 범위별 기존 완료 증거, 원 케이스 완료를 막는 미해결 항목이 없다는 판정, 완료 뒤 독립 유지 작업과 원 케이스 종결 효과를 표시한다. 현재 오너가 명시 확인한 때만 완료하고 취소하면 기존 활성 상태와 저장 입력을 유지하며 완료 사건을 만들지 않는다.
- 완료 뒤 undo·원 케이스 재개는 제공하지 않고 이후 새 오류·분쟁은 `DEC-038`의 범위별 연결 정정 케이스로 처리한다. 확인 또는 취소 결과를 감사하며 새 승인 역할·2인 승인·재개 상태를 만들지 않는다.

## DEC-077·RULE-077 연결 정정 보상 실행 계약

- `UNK-076`은 사용자 답변 A로 `ANSWERED` 처리되어 `DEC-077`과 `RULE-077`로 닫혔다.
- 현재 오너가 보상 사건 실행 직전에 대상 연결 정정 케이스·원 케이스·결과 배분·부분 수량·원 resolution 버전·커밋 증거·정정/보상 유형·사유·증빙·simulation별 불가역 효과·현재 정정 케이스 버전을 확인한다.
- 확인된 현재 정정 케이스 버전의 유일 실행 참조로만 carrier·warehouse·settlement simulation 보상 사건을 시작한다. 취소하면 사건·부수효과 없이 저장 입력·체크포인트를 유지하고 결과를 감사한다.
- 실행 커밋된 정정 결정·보상 사건은 수정·취소·재개하지 않는다. 추가 오류·분쟁은 같은 연결 정정 케이스 안에 원 사건을 불변 참조하는 새 후속 정정·보상 사건으로 추가한다.
- 이 계약과 기존 권위로 64개 상태 셀·88개 screen-axis cell·1012개 action cell을 완전 매핑했다. 리비전 79의 명시 승인은 완료됐고 구현 작업은 아직 만들지 않았다.

## 구현 착수 전 `DEC-034`~`DEC-077` 수용 기준

- `AC-001`: 거래처 포털과 내부 대리 등록에서 제출 전 draft의 품목·부분 수량·사유·증빙·추적값을 수정하거나 draft를 삭제하고 제출할 수 있어야 한다. 제출 순간 원 요청 스냅샷을 불변으로 고정하고 거래처와 현재 케이스 오너 모두 원 제출값을 삭제·덮어쓰지 않아야 한다. 제출 뒤 변경·취소는 원 스냅샷에 연결된 별도 요청 또는 정정 사건으로만 기록한다. 거래처 사용자는 대상 품목·부분 수량의 `DATA-011` inbound 반품 운송 상태가 `IN_TRANSIT`가 되기 전까지만 직접 접수할 수 있고 `IN_TRANSIT`부터 해당 범위의 동작이 차단되어야 한다. 다른 범위는 자체 상태로 판정하고 현재 오너가 반영한 사건은 `DEC-041`의 최소 되돌림·물리 사실 보존·정리 증거 게이트를 적용하며, 필드·목적별 고정 최소 단계·증거 매핑은 `DEC-043`의 확정 매핑을 표시한다. `DEC-042`에 따라 이후 보완은 현재 오너가 승인 또는 입고 불일치 재결정을 위해 이미 연 추가정보요청의 증빙·답변만, 이의는 `DEC-047`의 통지 성립 시각부터 `DEC-049`의 연속 336시간이 지나기 전까지 폐기비 문제만 허용하고, 최초 final resolution 확정 뒤 미커밋 범위의 현재 오너 결정 재개와 실행 커밋 뒤 연결 정정을 각각 `DEC-041`·`DEC-037`과 `DEC-038`로 분기하며 그 밖의 일반 변경·취소를 차단하고 혼합 쟁점을 범위별로 나눠야 한다. `DEC-044`에 따라 같은 생성·제출 멱등 키와 같은 입력을 반복해도 케이스·draft·제출 스냅샷은 하나만 생기고 기존 진행·결과를 반환하며 같은 키의 다른 입력은 충돌로 차단해야 한다.
- `AC-002`: 제출 뒤 연결 변경·취소 요청 또는 정정 사건의 대상 품목·부분 수량·사유·증빙·추적값, 수행자·시각과 현재 케이스 오너의 반영 여부·사유를 감사 이력으로 추가하고 원 요청 스냅샷은 그대로 보존해야 한다. `DEC-041`에 따라 변경 필드가 처음 무효화하는 단계까지만 대상 범위를 되돌리고, 관찰된 운송·입고·검수 물리 사실을 보존하며, 무효 미커밋 지시·결정·참조의 취소·재연결 증거가 모두 확인된 뒤 재처리해야 한다. 필드·목적별 고정 최소 단계·증거 매핑은 `DEC-043`에 따라 검증한다. 같은 범위 예상 버전의 동시 승인에서는 한 건만 원자 커밋되고 나머지는 버전 충돌과 최신 상태를 반환해야 한다.
- `AC-003`: 결정적 carrier simulation이 `DATA-011` 대상 품목·부분 수량 inbound 회수 범위를 `IN_TRANSIT`로 전이하면 사건·시각을 기록하고 해당 범위의 거래처 직접 변경·취소 접수만 차단해야 한다. 운송장 등록만으로는 접수를 차단하지 않고 거래처 부담 회수 운송장 추적 갱신 권한과 다른 범위의 처리는 유지해야 한다. 현재 오너가 반영한 변경으로 재처리하더라도 관찰된 `IN_TRANSIT` 사건·시각과 실제 입고·검수 사실은 삭제하거나 이전 상태로 역전하지 않고 불변 관찰로 보존해야 한다. 같은 입고·검수 제출 또는 상태 전이 재시도는 기록·상태를 한 번만 반영하고 기존 결과를 반환해야 한다.
- `AC-004`: `DEC-040`의 `IN_TRANSIT` 직접 접수 마감과 `final resolution` 최초 확정·재개·실행 커밋을 서로 다른 경계로 검증하고, 이미 접수된 사건은 `DEC-041`에 따라 영향이 처음 시작되는 단계까지만 대상 범위를 되돌리고 물리 사실을 보존하며, 필수 취소·재연결 증거가 모두 확인된 뒤 재처리한다. 필드·목적별 고정 최소 단계·증거 매핑은 `DEC-043`의 확정 매핑을 표시한다. `DEC-039`에 따라 준비된 품목·부분 수량별로 `final resolution` 최초 확정을 독립 적용한다. 현재 케이스 오너만 같은 Return Line의 `final resolution` 코드별 결과 배분·부분 수량 독립 실행 범위를 최초 확정하거나 다시 연다. 범위마다 코드·부분 수량·사유·오너·시각·버전·커밋 상태를 저장하고 `REFUND` 지급, `REPLACEMENT` 교환 출고, `RETURN_TO_CUSTOMER` 운송사 실물 인계 또는 거래처 직접 인수 서명, `NO_CREDIT` 폐기 실행 시작 전의 선택한 미커밋 범위만 필수 사유로 재개할 수 있어야 한다. 재개 대상 범위는 새 실행 차단 → 미커밋 운송·정산 지시 취소·무효화 → 재고·격리·금액 참조 재계산·재연결 → 기존 통지 `SUPERSEDED`·정정 통지 `PENDING` → 단계별 증거 확인을 순서대로 수행하고, 모두 성공한 때만 새 resolution 버전을 활성화해야 한다. 실패하면 그 범위만 `REOPEN_CLEANUP_HOLD`로 유지한다. 한 범위가 커밋되면 해당 범위만 재개를 차단하고 미커밋 형제 범위는 다시 열거나 재개 없이 기존 확정 결과대로 계속 처리할 수 있어야 한다. 한 Return Line과 케이스의 커밋·미커밋·정리 보류 혼재와 다른 범위·품목의 계속 처리가 유효해야 한다. `RETURN_TO_CUSTOMER` 라벨 생성·결과 통지와 `NO_CREDIT` 결과 통지·격리·금액 계산만으로는 해당 미커밋 범위의 재개를 차단하지 않아야 한다. 커밋 뒤 오류·분쟁 범위에는 별도 연결 정정 케이스를 만들고 원 케이스·범위·resolution 버전·커밋 증거를 불변 참조하며, 현재 케이스 오너가 정정·보상 유형과 사유·증빙을 결정하고 해당 simulation이 보상 사건을 실행·기록하는 동안 다른 범위와 원 케이스 완료가 계속돼야 한다. `REFUND`를 포함한 simulation은 결과 배분·부분 수량 범위·resolution 버전·동작별 유일 실행 참조로 한 번만 실행되고 재시도에는 기존 진행·성공·실패 결과를 반환해야 한다. `DEC-048`에 따라 모든 `NO_CREDIT` 결과 배분·부분 수량의 폐기 증거 또는 물리적 예외 해결이 확인되지 않으면 현재 오너의 케이스 완료를 차단하고, 폐기비 정산 예외·이의는 이 물리 게이트와 독립 추적해야 한다.
- `AC-005`: 업무 목록과 케이스 작업공간은 불변 원 요청 스냅샷, 연결 변경·취소 요청 또는 정정 사건, 대상 품목·부분 수량, 현재 오너의 반영 판단·감사 계보를 구분하고 준비된 품목·부분 수량별 독립 최초 확정 상태를 표시한다. 대상 품목·부분 수량별 inbound 반품 운송 상태·`IN_TRANSIT` 전이 시각과 거래처 직접 접수 가능·종료 상태를 표시한다. 이후에는 `DEC-042`의 승인 또는 입고 불일치 재결정용 추가정보요청 보완, `DEC-047` 통지 성립 시각부터 336시간이 지나기 전까지의 `NO_CREDIT` 폐기비 이의, 최초 final resolution 확정 뒤 미커밋 범위의 현재 오너 결정 재개, 실행 커밋 뒤 연결 정정, 일반 변경·취소 접수 차단과 혼합 쟁점의 범위별 분기 상태를 표시한다. 또한 같은 Return Line의 결과 배분·부분 수량 범위마다 최초 확정·현재 활성 버전·`COMMITTED`·`UNCOMMITTED`·`REOPEN_CLEANUP_HOLD`·재개 가능 여부와 정리 단계·증거 상태를 구분하고 케이스와 Return Line의 혼재 상태를 요약한다. carrier simulation과 결정적 로컬 상태 저장소가 기록한 `RETURN_TO_CUSTOMER` 실물 인계·직접 인수 서명과 `NO_CREDIT` 폐기 실행 시작은 참조 범위의 커밋으로, 라벨·결과 통지·격리·금액 계산은 비커밋으로 표시한다. 재개·정리 통제 행동은 현재 케이스 오너의 적격 미커밋 범위에만 제공하고 커밋된 범위와 창고 담당자·정산 담당자에게는 제공하지 않는다. 미커밋 형제 범위가 재개 없이 계속 처리되고 다른 범위와 품목도 계속됨을 표시한다. 커밋된 범위의 별도 연결 정정 케이스, 원 범위·버전·커밋 증거, 현재 오너의 정정·보상 결정과 simulation 실행 상태를 원 케이스 완료와 구분해 표시한다. 목록과 작업공간은 기존 진행·결과, 입력 충돌, 버전 불일치와 최신 상태 재조회 결과를 표시해야 한다. 목록과 작업공간은 `NO_CREDIT` 범위별 폐기 증거·미해결 물리 예외·완료 게이트 충족 여부와 케이스 완료 가능 상태를 표시하고, 폐기비 정산 예외·이의 상태는 물리 완료와 분리해 표시해야 한다.
- `AC-006`: 제출 순간 불변 원 요청 스냅샷과 제출 뒤 연결 변경·취소 요청 또는 정정 사건·대상 품목·부분 수량·현재 오너 반영 판단을 삭제·덮어쓰기 없이 재구성할 수 있어야 한다. `DATA-011` 범위별 `IN_TRANSIT` 전이 사건·시각, 직접 접수 종료 판정과 차단된 동작을 원 요청·연결 사건 계보와 함께 재구성하고 다른 범위·운송 추적 갱신이 계속됐음을 구분해야 한다. 감사 이력은 `DEC-041`에 따른 최초 무효화 단계, 보존한 물리 사실, 취소·재연결 대상과 증거, 재처리 시작을 재구성할 수 있어야 한다. 필드·목적별 고정 최소 단계·증거 매핑은 `DEC-043`의 확정 매핑으로 구분하고, `DEC-042`의 허용된 추가정보요청 보완·`DEC-047` 통지 성립 시각부터 336시간이 지나기 전까지의 `NO_CREDIT` 폐기비 이의·미커밋 재개·커밋 뒤 연결 정정·일반 변경·취소 차단·혼합 쟁점 범위별 분기 판정과 대상 범위를 재구성할 수 있어야 한다. 최초 확정·재개·정리·새 버전 활성화·정리 보류·실행 커밋마다 케이스·Return Line·결과 배분 범위 참조, 코드, 부분 수량과 시리얼·로트 신원, 범위별 `COMMITTED`·`UNCOMMITTED`·`REOPEN_CLEANUP_HOLD`, 수행자·시각·필수 사유·이전·새 버전, 취소·무효화·재계산·재연결·통지 대체·단계별 증거를 별도 불변 감사 이벤트로 기록하고 기존 확정 기록을 삭제·덮어쓰지 않는다. 한 Return Line과 케이스의 혼재 상태, 미커밋 형제 범위의 계속 처리와 각 범위의 버전 계보를 재구성할 수 있어야 한다. 후속 실행·예외·이의·금액 조정과 커밋 뒤 연결 정정은 대상 범위·버전과 구분한다. 연결 정정 케이스는 원 케이스·범위·resolution 버전·커밋 증거를 불변 참조하고 현재 오너의 정정·보상 유형·사유·증빙 결정과 carrier·warehouse·settlement simulation 보상 사건을 기록한다. 감사 이력의 멱등 키·입력 요약·예상 및 실제 버전·효과 참조·반환 결과로 최초 시도·재시도·충돌·simulation 효과를 재구성해야 한다. 감사 이력은 모든 `NO_CREDIT` 수량별 폐기 증거 또는 물리 예외 해결과 그 뒤 현재 오너의 케이스 완료 결정을 재구성하고, 폐기비 정산 예외·이의가 독립 연결 작업으로 계속됐음을 구분해야 한다.
- `AC-007`: 거래처 포털은 제출 전 draft의 품목·부분 수량·사유·증빙·추적값 수정·draft 삭제·제출을 제공하고, 제출 뒤 불변 원 요청 스냅샷과 연결 변경·취소 요청 또는 정정 사건·현재 오너 반영 상태를 외부 공개 범위에서 구분해야 한다. 대상 범위가 `IN_TRANSIT`가 되기 전에는 연결 변경·취소 직접 접수 동작을 제공하고 `IN_TRANSIT`부터 차단하며, 거래처 부담 회수 운송장 추적 갱신과 기존 허용 보완·이의는 직접 접수 마감과 구분한다. 현재 오너의 반영 결과에는 `DEC-041`의 최소 되돌림·물리 사실 보존·정리 증거 상태를 읽기 전용으로 표시하고, 필드·목적별 고정 최소 단계·증거 매핑은 `DEC-043`의 확정 매핑을 표시한다. `DEC-042`에 따라 포털은 현재 오너가 승인 또는 입고 불일치 재결정을 위해 이미 연 추가정보요청의 증빙·답변 보완과 `DEC-047` 통지 성립 시각부터 336시간이 지나기 전까지의 `NO_CREDIT` 폐기비 이의만 허용된 제출 동작으로 제공하고, 미커밋 재개·커밋 뒤 연결 정정은 외부 공개 범위에서 읽기 전용으로 표시하며 그 밖의 일반 변경·취소를 제공하지 않고 혼합 쟁점을 범위별로 구분한다. 최초 확정 결과·현재 활성 버전과 외부 공개 재개·재확정·실행 커밋·기존 통지 `SUPERSEDED`·정정 통지 `PENDING`·`REOPEN_CLEANUP_HOLD` 상태를 읽기 전용으로 표시하며 거래처 사용자의 결과 재개 제출을 제공하지 않는다. 자기 거래처 조직의 외부 공개 연결 정정 케이스 상태는 읽기 전용으로 표시하고 정정·보상 결정이나 simulation 실행 행동은 제공하지 않는다. 포털 생성·제출·연결 변경·회수 추적 갱신·이의 제출 재시도가 중복 기록·상태 전이를 만들지 않고 기존 결과와 충돌 상태를 자기 조직 범위에서 표시해야 한다. 거래처 포털은 자기 조직의 외부 공개 범위에서 `NO_CREDIT` 폐기 증거·물리 예외 해결·케이스 완료 상태와 폐기비 정산 예외·이의를 읽기 전용으로 구분하며 케이스 완료 행동을 제공하지 않아야 한다.

### `DEC-054` 폐기 실패·부분 성공 수용 보강

- `AC-004`: 폐기 실패 또는 부분 성공 범위의 성공 처분 사실·수량을 보존하고 실패·잔여 수량만 보류하는지 검증한다. 현재 오너가 결정적 로컬 창고 상태와 폐기 인계·실행 증거를 근거로 책임 주체·추가 비용 부담과 산정 근거·허용된 재시도 또는 대체 처분 경로·잔여 수량·종결 조건을 건별 결정·기록하고 물리 복구 작업을 창고 담당자에게 배정하며, 배정 창고 담당자가 관찰 사실·성공 수량을 보존해 `DEC-051` 필수 증거로 실행·기록한 뒤 현재 오너가 종결 조건을 확인해야 해당 예외를 해결한다.
- `AC-005`: 목록·케이스·창고 작업공간에 영향 범위, 성공 처분 사실·수량, 실패·잔여 수량, 결정적 로컬 창고 상태와 폐기 인계·실행 증거, 현재 오너의 책임/추가 비용/재시도 또는 대체 처분/잔여 수량/종결 결정·배정·확인, 창고 실행·증거, 근거 또는 실행 증거 누락에 따른 실패·잔여 범위만 보류·다른 범위 및 원 케이스 계속 상태를 역할별로 표시하는지 검증한다. 근거 없는 자동 재시도·책임·추가 비용 고정이나 거래처 합의 선행 동작을 제공하지 않아야 한다.
- `AC-006`: 감사 이력만으로 영향 범위·부분 수량·시리얼 또는 로트, 성공 처분 사실·수량과 실패·잔여 수량, 결정적 로컬 창고 상태와 폐기 인계·실행 증거, 책임 주체, 추가 비용 부담·산정 근거, 허용된 재시도 또는 대체 처분 경로, 종결 조건, 현재 오너 결정·배정·확인, 창고의 관찰 사실·성공 수량 보존과 `DEC-051` 필수 증거, `LOCAL WAREHOUSE STATE` 또는 `SIMULATION` 원천, 보류·해결·종결을 재구성할 수 있는지 검증한다. 실제 외부 연동·금전·재고 부수효과가 없어야 한다.

### `DEC-050` `RETURN_TO_CUSTOMER` 배송 예외 수용 보강

- `AC-004`: 운송사 실물 인계로 커밋된 `RETURN_TO_CUSTOMER` 배송 범위에 분실·파손·배송 실패·미인수 예외가 발생하면 범위별 연결 정정 케이스가 생성되고 현재 오너만 carrier simulation 증거를 검토해 운송사 클레임·추적 가능한 재발송·계속 보관·대체 처분과 추가 비용 처리를 건별 결정·기록하는지 검증한다. 선택된 simulation 사건과 필수 증거 뒤 현재 오너가 종결하고 원 resolution은 다시 열리지 않으며 다른 범위와 원 케이스 완료가 계속되는지 확인한다. 거래처 직접 인수 서명 미수신은 커밋되지 않고 `DEC-035`의 미커밋 완료 차단으로 남으며 `DEC-050` 연결 정정으로 합치지 않는지 함께 확인한다.
- `AC-005`: 업무 목록·케이스 작업공간에 `DEC-050` 대상 범위, carrier 예외 증거, 현재 오너 결정, simulation 실행·필수 증거·종결과 원 resolution 비재개·다른 범위 및 원 케이스 완료 계속이 표시되고 현재 오너에게만 결정·종결 동작이 제공되는지 검증한다.
- `AC-006`: 감사 이력만으로 `DEC-050` 연결 정정 케이스의 불변 원 참조, carrier 예외 증거, 현재 오너의 경로·추가 비용 결정, simulation 보상 사건·필수 증거·종결과 원 resolution 비재개·다른 범위 및 원 케이스 완료 계속을 재구성할 수 있는지 검증한다.
- `AC-007`: 거래처가 자기 조직 `DEC-050` 연결 정정 케이스 중 기존 권한 계약에서 외부 공개 대상으로 분류된 상태와 결과만 읽기 전용으로 보고 결정 동작은 사용할 수 없으며 원 resolution 비재개와 다른 범위·원 케이스 완료 계속을 확인할 수 있는지 검증한다. 구체 공개 필드가 이 결정으로 확장되지 않았는지 함께 확인한다.

### `DEC-045`·`DEC-047` 알림 수용 보강

- `AC-004`: `NO_CREDIT` 필수 내용과 단일 통지 참조가 자기 조직 포털 원장에 원자 게시되고 거래처 조회 가능 시각이 통지 성립·연속 336시간 시작으로 기록되고 336시간이 지난 순간 보관·이의 기간이 함께 끝나는지 검증한다. 요율 미확정이면 정산 예외와 근거를 식별한다.
- `AC-005`: 목록과 작업공간에 단일 통지 참조, 포털 게시·조회 가능 시각, 연속 336시간 시작·종료·이의 마감·폐기 예정 기준, 주말·공휴일 포함·연장 없음, 같은 참조의 이메일 시도·실패·재전송과 현재 오너 에스컬레이션을 표시하고 이메일 실패를 물리 보류로 표시하지 않는지 검증한다.
- `AC-006`: 필수 내용 스냅샷, 포털 원자 게시 커밋·조회 가능 시각, 이메일 시도·실패·같은 참조 재전송·현재 오너 에스컬레이션, 통지·물리 처리 비롤백을 감사 이력에서 재구성할 수 있는지 검증한다.
- `AC-007`: 거래처가 자기 조직의 필수 통지 내용·단일 참조·성립 시각·그 시각부터 336시간 뒤의 마감과 보조 이메일 상태만 확인하고 다른 조직·내부 전용 정보를 보지 못하는지, 별도 수령 확인 없이 포털 게시 성립을 확인할 수 있는지 검증한다.

### `DEC-046`·`DEC-057` 기록·패키지·증빙 수용 보강

- `AC-001`, `AC-003`, `AC-004`, `AC-006`, `AC-007`: 모든 지원 증빙은 JPG·PNG·PDF만 허용하고 영상은 차단한다. 파일당 최대 `20 MB`이고 별도 파일 개수·제출 단위 총량 상한은 두지 않는다. 확장자·MIME·파일 시그니처 일치와 결정적 로컬 악성 파일 검사를 모두 통과한 파일만 확정하며 실패·시간 초과·검사기 오류에는 실패 사유와 안전한 파일 재선택을 표시하고 다른 유효한 Draft 입력·기존 안전 첨부를 보존한다.
- `AC-002`, `AC-003`, `AC-004`, `AC-005`, `AC-006`, `AC-007`: 현재 케이스 오너만 해당 케이스의 전체 내부 패키지를 다운로드하고 거래처는 자기 조직의 외부 공개 패키지만 다운로드한다. 비오너 RMA Agent·창고·정산 담당자의 전체 내부 패키지 다운로드와 창고·정산의 배정 밖 일괄 다운로드를 차단한다.
- `AC-001`, `AC-002`, `AC-003`, `AC-004`, `AC-005`, `AC-006`, `AC-007`: 제출 전 draft 삭제는 유지하되 제출 이후 기록 hard-delete와 구분하고, 어떤 역할에도 자동 삭제 설정·실행 또는 수동 hard-delete UI를 제공하지 않는다.
- `AC-002`, `AC-006`: 정확한 보존 기간·자동 삭제·삭제 증명은 `UNK-023`의 비차단 후속 정책이며 구현·수용 기준에서 수치·시점·삭제 증명 형식을 만들지 않는다.
