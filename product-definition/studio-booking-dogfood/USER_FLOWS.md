## FLOW-001
- Status: CURRENT
- Name: 고객 예약 즉시 확정
- Steps: 시스템이 스튜디오 현지 날짜의 오늘부터 포함 90일째까지 슬롯 조회를 허용하고 범위 밖 날짜는 표시하지 않는다. → 시스템이 촬영 시작까지 2시간 이상 남은 슬롯만 표시한다. → 고객이 30분 경계의 시작·종료를 선택하며 예약 길이는 1~8시간으로 제한된다. → 시스템은 전후 30분 버퍼를 포함한 전체 구간이 영업시간 안에 있는지 검사하고 버퍼가 실제 가용 슬롯에 미치는 영향을 안내한다. → 고객이 촬영 인원을 필수 입력하고 해당 인원을 수용하는 공간 하나를 선택한다. → 시스템이 해당 공간과 호환되는 장비만 보여준다. → 고객이 장비 품목별 수량을 선택한다. → 고객이 필수 이름·이메일과 선택 전화번호·촬영 메모를 입력하고 수집 목적 및 필수·선택 표시를 확인한다. → 고객이 최종 확인을 누른다. → 시스템이 서버 시각으로 촬영 시작 2시간 전 경계를 다시 검사한다. → 시스템이 촬영 인원과 공간 수용 인원, 시간 규칙, 버퍼를 포함한 공간 독점 점유와 모든 장비 품목별 합계 가용성을 원자적으로 검사한다. → 모두 가용하고 호환되면 점유와 예약 확정을 함께 완료한다. → 2시간 경계를 넘었으면 선택 내용을 보존한 채 가능한 다음 슬롯을 표시한다. 경쟁 commit 충돌이면 아무 예약·부분 점유도 만들지 않고 고객 입력과 새 대안에도 호환되는 선택을 보존한다. 장비 수량 부족이면 같은 시간 최대 수량·동급 호환 대체 장비·원래 수량 가능 최신 시간을 순서대로 표시하고 선택 후 전체를 재계산한다.
- Screens: SCR-004, SCR-001

## FLOW-002
- Status: CURRENT
- Name: 이메일 링크로 예약 관리 접근
- Steps: 고객이 예약에 사용한 이메일로 관리 링크를 요청한다. → 명백한 이메일 형식 오류면 필드 오류를 표시한다. → 유효한 형식이면 일치 예약 존재 여부와 무관하게 같은 중립 응답을 준비한다. → 일치 예약이 없으면 토큰·메일·기존 토큰 상태를 변경하지 않고 중립 응답을 표시한다. → 일치 예약이 있으면 이메일별 60초·시간당 5회 한도를 검사한다. → 한도 초과면 토큰·메일·기존 토큰 상태를 변경하지 않고 중립 응답과 재시도 가능 시점을 표시한다. → 한도 이내면 새 일회용 토큰을 발급한 뒤 이전 미사용 토큰을 폐기한다. → 시스템이 관리 링크를 이메일로 보낸다. → 고객이 유효한 링크를 사용한다. → 시스템이 토큰을 사용 완료 처리하고 30분 관리 세션을 만든다. → 고객이 해당 예약 관리 화면에 접근한다. → 변경·취소 제출 시 서버가 세션 만료를 재검사한다. → 만료됐다면 mutation 없이 새 링크 인증을 거쳐 직전 입력을 복구한다.
- Screens: SCR-002, SCR-003

## FLOW-003
- Status: CURRENT
- Name: 운영시간 설정 및 충돌 검토
- Steps: 운영자가 스튜디오 공통 요일별 반복 영업시간을 편집하거나 특정 날짜의 완전 휴무·연장·단축 예외를 만든다. → 시스템이 날짜 예외 우선순위를 적용한 변경안을 계산한다. → 시스템이 기존 확정 예약의 버퍼 포함 점유 구간과 충돌하는지 검사한다. → 충돌이 없으면 변경을 확정한다. → 충돌이 있으면 예약을 자동 취소하지 않고 충돌 목록을 표시한다. → 운영자는 각 충돌에 예외 유지·고객 협의 후 변경·운영자 취소 중 하나와 사유를 기록한다. → 모든 충돌 기록이 완료되면 영업시간 변경을 확정한다. → 예외 유지 예약은 기존 점유를 유지하고 신규 예약에는 새 영업시간을 적용한다. → 변경·취소된 예약은 이메일 delivery record를 생성하며 발송 실패도 상태 변경을 롤백하지 않는다.
- Screens: SCR-005

## FLOW-004
- Status: CURRENT
- Name: 고객 이메일 알림 전달
- Steps: 예약 확정·변경·취소·운영자 조치 또는 관리 링크 이벤트가 업무 transaction에서 확정된다. → 시스템이 이벤트와 수신 예약을 참조하는 별도 delivery record를 만든다. → 이메일 제공자에 발송을 요청한다. → 성공 또는 실패 결과와 시각을 delivery record에 기록한다. → 실패하더라도 원래 예약·운영 상태는 유지한다.
- Screens: SCR-006

## FLOW-005
- Status: CURRENT
- Name: 고객 및 운영자 예약 취소
- Steps: 인증된 고객 또는 운영자가 확정 예약의 취소를 요청한다. → 고객 요청이면 서버가 현재 시각이 촬영 시작 정확히 48시간 전 또는 그 이전인지 검사한다. → 마감 이후면 mutation 없이 운영자 문의를 안내한다. → 운영자 요청이면 필수 취소 사유와 가능한 대체 시간·공간·장비안을 먼저 준비해 기존 고객 동의 lifecycle로 제안한다. → 고객이 대체안에 동의하면 전체를 원자적으로 변경하고 취소하지 않는다. → 합의 실패 또는 운영 불가이면 운영자 취소를 진행한다. → 허용된 취소는 예약 상태 변경과 공간·장비 점유 해제를 원자적으로 commit한다. → 대체·취소 이메일 delivery record와 감사를 생성하며 결제·환불·보상·크레딧은 처리하지 않는다.
- Screens: SCR-003, SCR-007

## FLOW-006
- Status: CURRENT
- Name: 고객 예약 변경
- Steps: 인증된 고객이 예약 변경을 시작한다. → 시스템이 원래 촬영 시작 48시간 전까지인지 검사한다. → 고객이 새 촬영 인원·시간·공간·장비를 선택한다. → 서버가 촬영 인원과 공간 수용 인원, 시간·영업시간·버퍼·호환성·공간 독점·장비 수량 가용성을 모두 재검증한다. → 시스템이 새 구성 총액과 기존 가격 snapshot 차이를 표시하고 고객 확인을 받는다. → 서버가 새 점유 확보, 예약 변경, 기존 점유 해제를 원자적으로 commit한다. → 변경 commit과 함께 새 가격 snapshot을 확정한다. → 충돌 또는 검증 실패면 어떠한 새 점유도 남기지 않고 기존 예약을 보존한다. → 성공하면 변경 이메일 delivery record를 생성한다.
- Screens: SCR-003, SCR-004, SCR-008

## FLOW-007
- Status: CURRENT
- Name: 예약 가격 계산 및 snapshot 확정
- Steps: 운영자가 공간·장비 시간당 요금을 입력하면 2원 단위 정수인지 검증하고 실패 시 기존 요금을 보존한다. → 시스템이 고객 촬영 시간을 30분 단위로 계산한다. → 공간 시간당 요금과 장비 품목별 시간당 요금×수량을 비례 계산하고 버퍼는 제외한다. → 고객에게 구성요소와 총액을 표시한다. → 신규 예약 확정 시 적용 단가·수량·시간·항목별 금액·총액 snapshot을 고정한다. → 운영자 요금 변경은 기존 snapshot을 수정하지 않는다. → 예약 변경 시 기존 snapshot과 새 구성 총액 차이를 표시하고 고객 확인 후 새 snapshot을 변경 commit과 함께 확정한다.
- Screens: SCR-001, SCR-008, SCR-009

## FLOW-008
- Status: CURRENT
- Name: 예약 고객 개인정보 익명화
- Steps: 최고 권한 운영자가 예약에 사유와 사건/문서 참조를 입력해 legal hold를 설정할 수 있다. → 시스템은 주체·시각·전후 상태를 append-only 감사 기록에 추가하고 고객 개인정보·관련 delivery·감사 기록에 hold를 적용한다. → 시스템이 종료·취소 후 1년이 지난 예약을 찾는다. → 활성 legal hold가 있으면 익명화를 보류하고 보류 상태를 기록한다. → hold가 없으면 이름·이메일·전화번호·촬영 메모를 비가역 익명화한다. → 예약 시간·공간·장비·가격 snapshot·상태·비식별 운영 통계는 유지한다. → 최고 권한 운영자가 별도 사유로 hold를 해제하면 append-only 감사를 추가하고 해당 예약의 기한을 다시 평가한다.
- Screens: SCR-010

## FLOW-009
- Status: CURRENT
- Name: 운영자 권한 및 개인정보 접근
- Steps: Owner가 운영자 이메일을 초대한다. → 초대받은 사용자가 해당 주소를 확인하고 비밀번호를 설정한다. → 사용자가 TOTP를 등록하고 10개 일회용 복구 코드를 한 번만 표시·다운로드한다. → 모든 단계를 마치면 계정이 활성화된다. → 운영자는 이메일·비밀번호와 TOTP 또는 미사용 복구 코드를 검증해 로그인한다. → 사용한 복구 코드는 즉시 폐기하고 사용을 감사한다. → 비밀번호 재인증 후 새 복구 코드 세트를 발급하면 기존 미사용 코드를 모두 폐기하고 재발급을 감사한다. → 비밀번호 재설정은 중립 요청 응답, 15분 이메일 링크, TOTP 또는 미사용 복구 코드를 모두 통과해야 한다. → 재설정 성공 시 기존 운영 세션을 모두 폐기하고 관련 성공·실패·폐기를 감사한다. → 비밀번호·TOTP 연속 실패 합계가 5회면 15분 잠그고 모든 실패·잠금·성공 초기화를 감사한다. → Owner는 사유를 기록해 다른 Staff 잠금을 즉시 해제할 수 있지만 자기 잠금은 해제할 수 없다. → 시스템이 Owner 또는 Staff 역할과 계정 활성 상태를 확인한다. → Owner는 운영자 초대·비활성화·역할 변경, legal hold, 전체 감사 조회를 수행할 수 있다. → Staff는 예약·공간·장비·영업시간·요금 운영만 수행한다. → 고객 개인정보 접근 시 업무상 필요한 예약인지 검사한다. → 허용·거부된 화면 조회와 금지된 개인정보 export 시도를 append-only 감사 기록에 남긴다. → Owner 또는 Staff가 Asia/Seoul 기준 기간·집계 단위를 선택해 핵심 운영 지표를 조회한다. → 집계 CSV 요청 시 개인정보와 예약 단위 행을 제외하고 결과가 10,000행 이내일 때만 파일을 생성한다.
- Screens: SCR-011, SCR-012, SCR-013, SCR-014

## FLOW-010
- Status: CURRENT
- Name: 공간·장비 설정 관리
- Steps: Owner 또는 Staff가 공간이나 장비를 생성하거나 기존 항목을 연다. → 이름·설명·사진·활성 상태와 공간 수용 인원 또는 장비 총수량을 입력하고 시간당 요금·호환성을 설정한다. → 시스템이 필드와 시간당 요금의 2원 단위 규칙을 검증한다. → 공간 수용 인원 하향, 장비 수량 감소 또는 자원 비활성화이면 확정 예약의 촬영 인원·점유와 충돌하는지 검사한다. → 충돌하면 변경을 적용하지 않고 충돌 예약 목록과 별도 처리 안내를 표시한다. → 충돌이 없으면 설정을 저장하되 기존 예약 snapshot과 점유는 변경하지 않는다. → 삭제 작업은 제공하지 않고 더 이상 판매하지 않을 자원은 비활성화한다. → 시스템은 주체·시각·전후 값·행위·결과를 감사 기록에 추가한다.
- Screens: SCR-015

## FLOW-011
- Status: CURRENT
- Name: 48시간 이후 운영자 변경 동의
- Steps: Owner 또는 Staff가 필수 사유와 시간·공간·장비·촬영 인원 변경안을 제출한다. → 시스템이 새 proposal version의 고객 동의 토큰을 생성하고 이메일 요청을 시도한다. → 토큰 발급과 이메일 요청이 모두 성공한 경우에만 이전 미사용 링크를 폐기하고 새 변경안을 유일한 활성안으로 만든다. → 링크는 발급 후 24시간 또는 원래 촬영 시작 중 먼저 오는 시점에 만료한다. → 고객이 링크에서 동의 또는 거절하면 서버가 latest proposal version 일치를 검사한다. → stale 링크면 mutation 없이 거부하고, 유효한 거절이면 변경안을 종료한 채 기존 예약을 유지한다. → 유효한 동의이면 commit 직전에 변경안 전체의 시간·영업시간·버퍼·호환성·수용 인원·가용성·가격을 다시 검증한다. → 통과하면 새 점유 확보·예약과 가격 snapshot 교체·기존 점유 해제를 원자적으로 commit한다. → 검증 또는 commit 실패면 기존 예약과 점유를 보존한다. → 요청·동의·거절·폐기·만료·변경 결과·알림을 감사하고 delivery record를 연결한다.
- Screens: SCR-016

## FLOW-012
- Status: CURRENT
- Name: 48시간 이후 취소 문의
